## 1. 产品输入、输出与运行边界

用户在 Web 聊天工作区创建项目和会话，粘贴原作，或导入 TXT／Markdown／DOCX；TXT/Markdown 支持 UTF-8、带 BOM 的 UTF-16 LE。单次导入上限 10 MB。原作被原样保存为 `source_text` 的固定版本，后续 Agent 只能依据该版本及有据可查的引用工作。通过导入表单保存后会自动为该版本排队启动 Step1；预算预检不通过时会明确显示已保存但未启动。聊天框粘贴原文仍由协调 Agent 识别并调用 `begin_adaptation`。当前**不支持 PDF 导入**。用户在对话中授权完整改编或指定阶段、回答 Agent 问题、确认或要求修改候选；界面还支持运行中消息 Steer/Queue、任务停止与恢复。

核心输出是经过程序校验的 Nexo `Project` JSON，即 `nexo_graph`；前端可查看、复制、下载同一固定版本。中途保存事件视图、分析、策略、方案、游戏事件、路线、画像、章节设计和章节 Graph。用户可通过“配置与运行数据”调整未来 Run 的配置、查看最新已保存产物和实际 Agent Run。应用没有自动写入 Nexo 编辑器、自动发布工程或完整 DSL 求解功能。

```
原作导入 source_text → 自动排队 Step1；聊天框粘贴 → 主 Agent 协调 → Step1 两个并行子 Agent
                                      ├─ 作品事件视图 + 全局分析
                                      └─ 人物事件视图
                         三份固定产物 → Step2 知识资产分析 Agent
                                      → 原作知识资产 → 一次确认
                         Step3–8 策略/方案/互动结构 → Step9–10 按章创作
                                          → 程序组装/校验 → nexo_graph
                                          → 可选 Step11 校验 Agent
```

系统服务由 FastAPI API、后台 Engine/worker、PostgreSQL 和文件 Blob 目录组成。Web 页面只是操作入口：关闭浏览器不会取消后台任务。主要入口是 `branch_agent/cli.py`、`branch_agent/app.py:create_app`、`branch_agent/engine.py`。模型调用适配、SDK Session 和模型审计在 `branch_agent/model_service.py`；主 Agent 工具在 `branch_agent/manager.py`；任务依赖、产物和确认在 `branch_agent/workflow.py`；数据库在 `branch_agent/storage.py` 与 `migrations/`。

## 2. Agent 分工与 SDK 调用方式

| Agent 配置键 | 职责 | 主要运行位置 |
| --- | --- | --- |
| `conversation_coordinator` | 保持用户对话控制权，理解授权范围，调用 Harness 工具推进阶段、提出确认或澄清、解释真实进度 | 主对话 Run；历史问答复用该 Agent |
| `source_global_parser` | 边读取原作边切分完整**作品事件**，分析因果、世界、主题和保留建议 | Step1 作品事件分支 |
| `source_character_parser` | 独立阅读原作，整理**主要人物及各自的事件链**；不读取作品事件视图，也不输出独立分析 | Step1 人物事件分支 |
| `source_knowledge_analyst` | 综合两套事件视图和全局事件分析，形成结构化原作知识资产 | Step2 |
| `adaptation_planner` | 形成玩家与改编策略、完整改编方案 | Step3–4 |
| `interaction_architect` | 设计游戏事件、补充叙事功能、结局路线和玩家画像 | Step5–8 |
| `chapter_designer` | 每章完整线性正文及互动设计 | Step9 |
| `chapter_writer` | 根据已确认章节设计生成章节 Graph | Step10 |
| `validation_agent` | 可选的最终内容审核；不替代程序 Graph 校验 | Step11 |
| `aux.summary`、`aux.format_repair` 等辅助运行 | 工作会话压缩、结构化输出格式修复、局部只读分析、历史答疑 | 独立辅助 Task/Run |

Step1 按两路专长 Agent 运行，Step2 使用独立分析 Agent。`prompts.py` 同时保存**创作职责**与可编辑的**Harness 执行规则**；`instructions()` 在 Run 时组合最终指令，配置页可预览。程序约束（授权、版本、依赖、权限、确认有效性、Schema 校验）仍由代码执行，不因提示词可编辑而放开。

`aux.summary` 使用独立的上下文摘要 Agent。配置页可编辑该 Agent 的职责，以及摘要任务的指令、模型参数和目标长度；最终 instructions 可预览。摘要仍是内部纯文本产物，输入来自 Harness 固定的历史归档，运行时不提供项目产物读取工具或 `ask_user`；配置了 Brave 凭据时可使用 `web_search`。主任务启动时会冻结摘要辅助配置，后续配置发布不回写已启动任务。

`aux.format_repair` 使用可配置的格式修复 Agent，由 Harness 在结构化输出有可定位格式错误时自动启动独立 Run/Session。输入绑定失败候选、当次固定 Schema 与精确校验错误。可解析的 JSON 使用带候选 SHA-256 的 JSON Pointer 局部补丁；无内容的多余字段可删除，根 `description` 中独有的文字仅可原样移入既有 `notes` 字符串数组。无法解析的 JSON 仅接受可机械验证的尾逗号修正；其他语法错误交回原阶段 Agent。Harness 合并并重新执行程序校验，修复 Agent 不补写缺失内容，也不能用外部搜索结果补充候选。`repair.format_max_rounds` 默认 1 次，`repair.content_max_rounds` 默认 5 次，分别计数；旧 `repair.max_rounds` 保留给其他返修路径。各次修复调用都消耗原任务预算，三个限额在父任务的固定配置快照中生效。

系统使用 OpenAI Agents SDK 的 `Agent`、`Runner.run`、`Runner.run_streamed`、`function_tool`、`Session`、`output_type`、`trace`。协调 Agent 在真实任务中以流式方式发送公开回复草稿；其他 Agent 保持结构化产物完成后保存，只向聊天区发送模型、工具及窗口进度。流式草稿以最终保存的回复为准，原始推理和完整产物不会作为进度事件发送。事件由数据库持久化，经 `/events` SSE 和会话 `/activity` 查询恢复，也不加入主 Agent 的 Session。DeepSeek 经兼容的 Responses 接口使用，默认模型为 `deepseek-flash`；OpenAI 模型可按 Agent 配置。DeepSeek 的 JSON Schema 使用非严格模式，返回后仍由 Harness 做本地 Schema 校验与修复。DeepSeek 可能忽略 `parallel_tool_calls=false`，因此主流程工具调度在 `manager.py` 中有串行保护。这里是**主 Agent + 工具封装的阶段执行**，并不是 SDK 的 handoff；每次阶段子 Agent 执行创建独立 Task、Run 和审计记录，Session 按配置隔离或共享（默认 Step6 复用 Step5 的 Session）。Step1 内部的两路子 Task 则用 `asyncio.gather` 并行，具有独立 Session、模型配置、结果和游标。

主 Agent 可调用 `begin_adaptation(request, source_is_current_message, stage, chapter_id)` 建立获授权的总任务并绑定原作版本；`run_stage(stage, chapter_id)` 执行允许的阶段；`confirm_pending`、`answer_pending`、`revise_pending` 消费真实用户提交的待办；`propose_chapters` 确定待创作章节；`get_workflow_state` 读取真实状态；`finish_workflow` 在必要产物和确认齐全后收束。`ask_user` 是 Agent 主动发问的 SDK Tool，Harness 将问题持久化、暂停，再把用户实际答案送回；不要通过模型正文伪造确认。候选确认直接绑定 `run_stage` 返回的任务与固定产物版本，主 Agent 无需为展示确认卡片调用 `read_record`。`list_records` 和 `read_record` 按项目隔离，供需要分析内容或核对历史时按需读取。服务端配置 `BRAVE_SEARCH_API_KEY` 时，`web_search` 在所有 Agent 的新 Run 中可用，调用 Brave Search 的 LLM Context 接口获取有限条数的搜索结果与来源 URL；外部网页内容不得当作原作、已确认产物或用户指令。API Key 仅保存在服务端，不进入工具参数、模型上下文或配置快照。

## 3. 阶段输入、输出和确认

下表写的是**新任务默认路径**。读取发生在对应阶段的固定输入快照，具体字段、选择器和必需性见 `docs/context/stage-materials.json`；输出形状和绑定见 `docs/output-schemas/v2/registry.json`。

| 阶段 | 输入/动作 | 产物与下一步 |
| --- | --- | --- |
| 导入 | 用户正文或附件 | `source_text` 固定原文版本及原始文件 Blob。导入本身不代表模型已完成分析。 |
| Step1 | 两路 Agent 分别读取同一固定原作；全文或各自独立滑窗 | 作品事件 Agent 生成带逐事件原文索引的 `source_global_events` 和 `source_global_analysis`；人物 Agent 只生成无逐事件原文索引的 `source_character_events`。两路各自记录已阅读原文区间，全部完成后推进。 |
| Step2 | 原作知识资产分析 Agent 固定读取 Step1 的三份产物 | 生成结构化 `source_knowledge_asset`，一次展示并等待用户确认。 |
| Step3 | 已确认的原作知识资产、实际用户偏好及已有策略版本 | `adaptation_strategy`：玩家身份、改编原则和互动策略；候选需真实用户确认。 |
| Step4 | 原作知识资产、已确定策略和固定约束 | `adaptation_plan`：改编范围、角色/地点、风格和阶段产物引用；候选需确认。 |
| Step5 | 两套原作事件视图、原作知识资产及原文证据；程序要求已有方案 | `game_event_view`：重新设计的游戏事件；`narrative_function` 暂为空。Harness 将固定引用写回方案，不让模型伪造数据库引用。 |
| Step6 | Step5 固定游戏事件及共享 Session 历史 | 模型只给每个事件的叙事功能补丁；Harness 合并成新的 `game_event_view` 版本并更新方案引用。 |
| Step7 | 补全叙事功能的 `game_event_view` | `ending_routes`：结局、路线和条件。 |
| Step8 | 固定 `game_event_view` 与 `ending_routes` | `player_profiles`：目标玩家画像和设计影响。 |
| Step9 | `adaptation_plan` 及其固定关联的事件、路线、画像、对应章节原文 | 每个 `chapter_id` 的 `chapter_design`：完整线性正文、互动点、入口出口契约；章节列表先确认。 |
| Step10 | 已确认的本章设计和固定原作片段 | 每章 `chapter_graph`；程序组装并校验最终 `nexo_graph`（Nexo Project JSON）。 |
| Step11 | 固定的最终 `nexo_graph` | 可选 `review_report`。即使关闭模型校验 Agent，程序 Schema 与可达性等检查仍执行。 |

大部分中间输出先作为候选保存；Agent 可以决定需要问什么、何时请求确认，用户的真实回答和确认由 Harness 绑定到当时展示的**明确产物版本与范围**。未确认不能伪装为已确认。Step1 的三份产物经校验后生效；Step2 的知识资产确认后供下游使用。`adaptation_strategy`、`adaptation_plan` 也允许在运行前人工写入项目产物链；两者的**账号默认值**在创建新项目时复制为该项目的普通版本，之后各项目独立演进。

模型输出契约也要分清：Step1 两个 Agent 各返回一个结构化 `ready` 信封。全局分支另含非空顶层 `analysis`，Harness 将其另存为纯文本 `source_global_analysis`；人物分支只返回 `character_views`，没有顶层分析，也没有逐人物事件的原文索引。两路仍各自填写固定 `source_ref`、`covered_source_anchors` 和 `remaining_source_anchors`，其中覆盖区间用于 Harness 校验阅读进度。Step2 返回结构化 `source_knowledge_asset`，程序绑定三份固定输入引用，内容包括故事前提、世界规则、主题、冲突、人物分析、关键事件和原作保留项。Step3–9 等阶段依注册 Schema 保存结果信封；Step6 返回针对已有事件 ID 的补丁；Step10 的章节 Graph 由程序纳入最终 `Project` 根对象。实际字段以 `docs/output-schemas/v2/registry.json` 绑定的 Schema 为准。

`EvidenceRef` 用 `record_id`、十进制 `version`、可选 `item_id`、`json_pointer` 指向项目内的**明确版本**。原文证据 `SourceAnchor` 用相同 `source_ref` 和绝对 UTF-16 `[start_utf16,end_utf16)`，或由程序唯一定位的准确短摘录；前端 JavaScript 的字符串索引与此口径一致。模型可提出候选引用，但真实记录身份、来源有效性、版本确认和产物生效由 Harness 校验与写入。

## 4. 长原文、上下文与恢复机制

**滑动窗口**：全局默认配置有 `context.step1_source.trigger_tokens`（默认 500000）和 `window_tokens`（默认 300000）。每路按自己的模型估算原文 token；原文超过阈值，或者虽未超过阈值但放不进该路安全输入预算时，改走该路滑窗。否则直接全文输入。窗口是原文的连续 UTF-16 半开区间 `[start,end)`，每路有自己的 Task、Session、Run、`cursor` 和窗口记录。当前代码用实际指令、工具定义、Schema、`runtime.source_index`、历史，以及全局分支的前窗累计分析或人物分支的前窗人物摘要预览请求；超预算时在 `window_tokens` 上限内缩小当次窗口。它**没有自动扩窗**。模型不得以摘要代替当前必须阅读的原文。
全文模式在真实请求组装后若仍超预算，或输出被截断，同样暂停并报告预算问题，不把该阶段记为完成；这不是改用摘要通关的信号。

作品事件分支只能在已形成的完整作品事件终点提交前缀，且提交点须与最后事件的来源锚点终点一致；人物分支不借用作品事件边界，也不要求逐人物事件锚点，可独立提交已检查的连续前缀。人物窗口如果没有主要人物事件，必须在 `notes` 用 `空人物事件区间：…` 给出具体说明，才能把该空区间计为已检查。程序核对两路覆盖起止、未完成尾部、来源版本、全局事件原文锚点和输出 Schema；任一路卡住会暂停总 Step1，保留另一分支已经验证的进度。最后两个事件视图分别合成；只有全局分支沿窗口累计分析，取最后一次的全本分析保存。超限、输出截断、缺少完整的全局事件或覆盖不连续都不记为完成。

**一般上下文预算**：`context.py` 取配置的输入上限、模型上下文窗口减去输出预留和安全余量中的较小者。必需材料不能静默裁掉；可选材料可按优先级收缩。`stage-materials.json` 定义固定版本选择、`auto/on_demand`、`full/index/ref`、选择器、完整覆盖责任和程序投影；其中标记为设计默认的 JSON 实际由 `configuration.py:initial_values()` 装入初始配置，具体行为仍须以运行时代码为准。Step2–8 的过大输入可由 `context_batching.py` 按稳定条目/范围拆批并维护 manifest；Step9–11 的完整必需输入超预算会暂停。Step1 使用上述滑窗，Step2 使用独立 Agent 分析固定产物。

**会话压缩**：`context.history_token_cap` 的全局默认值是 500000 tokens，它是单个 Session 旧历史的软阈值。当前 `compaction.py` 在工作会话接近输入预算的 75% 或达到此阈值时，尝试通过独立 `aux.summary` Run 压到约 50% 目标；无收益的可选压缩会跳过，实际输入硬预算仍须满足。源 HistoryRecord、SessionItem 世代和归档保持可追溯，摘要只供连续性参考，不能签发业务确认或取代固定材料。用户后来提出的“主 Agent 仅保留子 Agent 产物引用、各子 Agent 独立压缩”的更细策略记录于 `docs/context/上下文压缩策略开发方案.md`，尚需按文档继续设计和实现，不能当作现状。

**持久运行**：Task/Run 固定 ConfigVersion、原作及材料版本；ModelCall、ToolCall、ContextSnapshot 记录实际请求与结果。worker 使用租约、心跳、fencing token 和检查点恢复；外部调用结果不确定时不能盲目重发。项目删除会清除项目归属的待办/视图；新任务遇到上游版本变化按依赖状态处理。模型输出只形成候选，不直接修改历史确认。当前测试版在 `engine.py` 设 `COST_GATES_ENABLED=False`：仍估算并记录用量，但费用阈值不阻断；有效执行时间、模型轮次、重试与返修等限制仍需遵守。

## 5. 数据库、后台页面与 API

PostgreSQL 16 的初始表和关系见 `migrations/001_records.sql`、`002_relationships.sql`，后续迁移加账号配置草稿、SDK 本地 Trace 和账号产物默认值。核心记录大致分为：项目/会话/消息，`artifact`/`artifact_version`/`artifact_state`，用户 `decision`/`confirmation`，`task`/`run`/队列/检查点，`config_version`/`context_snapshot`/`model_call`/`tool_call`/Trace span，以及 Blob、依赖、事件、幂等记录和运行投影。业务产物通过 `artifact_id + version` 固定；数据库行并发修改还使用 `row_version` 乐观锁，这两种“版本”不能混淆。已有迁移按内容哈希核对，**不要改写已应用的迁移文件**；需要结构变化时添加新迁移。

“配置与运行数据”后台的**配置**部分有全局默认、Agent 配置、阶段配置、上下文摘要 Agent、格式修复 Agent、进阶 Harness 协议、最终校验。可设各路模型、推理等级、输出上限、最大模型轮次、材料、output_type/Schema、滑窗触发阈值和窗口大小，以及三类独立修复次数；创作职责与 Harness 规则分层可见，最终 instructions 可预览。编辑器内容自动保存为草稿，完整校验在“发布配置”时执行；发布生成新 ConfigVersion，仅后续 Run 使用新版本，既有 Run 保持原快照。高级协议层包含共通规则、Agent/阶段/运行/提问规则，默认折叠；调试创作内容通常改 Agent 创作职责和阶段创作任务即可。

**运行数据**展示每次 Agent Run 的实际 instructions、输入、工具调用、原始模型输出、用量、错误和本地 trace；`query` 在 UI 中叫“对话协调主 Agent”，`summarize` 叫“触发上下文压缩”。**产物监看**按项目选择数据种类，只读最新已保存版本及状态；`adaptation_strategy` 与 `adaptation_plan` 支持在项目内直接编辑，同一数据库版本链保存，也可设置账号级默认值给所有新项目。两处并非相互替代：Run 解释“怎么执行”，产物页说明“现在保存了什么”。前端主代码在 `branch_agent/static/app.js`，运行视图在 `runtime-view.mjs`，产物视图在 `artifact-view.mjs`。

业务 API 前缀是 `/api/branch-agent/v1`，路由均定义于 `branch_agent/app.py`；健康探针是根路径 `/health`。接手时重点看：

| 路径组 | 用途 |
| --- | --- |
| `/auth/*`、`/projects*`、`/projects/{p}/conversations*` | 登录、项目、对话和历史 |
| `/projects/{p}/source`、`/messages`、`/actions` | 原作导入、用户消息、待办卡片动作 |
| `/projects/{p}/status`、`/tasks/{id}/{action}`、`/queue/resume` | 后台任务状态、停止/恢复、排队请求 |
| `/projects/{p}/run-debug*`、`/records*`、`/references/resolve` | Run 审计和固定记录读取 |
| `/artifact-defaults`、`/projects/{p}/artifacts*` | 账号默认产物、项目当前产物/人工写入/版本下载 |
| `/account/config*`、`/projects/{p}/config*` | 草稿、预览、验证与发布配置 |
| `/projects/{p}/events`、`/conversations/{c}/activity`、`/release` | SSE 状态事件、会话运行记录回放、更新弹窗数据；健康探针另在根路径 `/health` |

HTTP 写入涉及项目访问校验、预期版本或幂等键；调接口前先看对应路由所要求的字段。`branch_agent/static/release-notes.json` 是更新弹窗展示的实际更新内容：**每次发布都应同步改它**，不能沿用旧版本的固定文案。

## 6. 本地运行、验证和修改路线

首次准备需 Python 3.10+、PostgreSQL 16；仓库已有 `.venv` 时可直接使用。根目录 `.env` 由服务端读取，环境变量优先；`DEEPSEEK_API_KEY` 是默认模型所需，选择 OpenAI 模型才需要 `OPENAI_API_KEY`。本地 `DATABASE_URL` 可指向 `postgresql:///branch_agent_local`，`BRANCH_DATA_DIR` 默认 `.data`。**不要提交或覆盖现有 `.env`、密钥、数据库和 `.data`。**

```bash
cd /Users/llj/HKU/Agent_Harness_Develop
.venv/bin/python -m branch_agent.cli migrate
./scripts/start.sh
# 本地页面 http://127.0.0.1:8767；另一个终端检查 /health 与 /api/branch-agent/v1/release
```

API 默认含内嵌 worker；需要拆进程时设 `BRANCH_EMBEDDED_WORKER=0 ./scripts/start.sh`，另启 `./scripts/worker.sh`，并确保两者使用相同数据库、文件目录和密钥。首次本地登录信息在 `.data/local-login.txt`。腾讯云现有测试实例使用同一 LocalAuth 适配器，首次初始化需 `BRANCH_LOCAL_PASSWORD`；之后凭据保存在持久文件，**仅修改环境变量不能轮换既有登录密码**。正式平台认证尚需替换适配器。编辑配置后发布，再发起新 Run 才能验证新指令。

```bash
.venv/bin/python -m pytest -q
node --test tests/*.test.mjs
.venv/bin/python docs/context/validate.py
.venv/bin/python docs/harness-data/validate.py
.venv/bin/python docs/output-schemas/v2/validate.py
git diff --check
```

真实模型联调与纯单测分开：单测中的 FakeModel/模拟 HTTP 不证明 DeepSeek 真实输出一定过 Schema，尤其长原文滑窗、Step2 三份输入的综合分析、知识资产确认和 Agent 主动 `ask_user`。`docs/live-model-smoke.md` 有较早的短篇端到端联调记录，不代表本工作区最新 Step1/Step2 协议已验收。修改阶段契约时同步检查：`prompts.py`、`configuration.py`、`workflow.py`、`engine.py`/`step1_execution.py`、`stage-materials.json`、Schema registry/文件、前端展示、测试与 release notes；新增产物还应检查固定输入、依赖失效和配置发布后的 Run 快照。

## 7. GitHub 与腾讯云部署流程

仓库的 `compose.yaml` 运行 PostgreSQL 16（`database` 持久卷）和应用（`files` 持久卷挂 `/data`）；应用仅映射主机 `127.0.0.1:8767`，公网 HTTPS 由宿主机 Nginx 反向代理。`Dockerfile` 基于 Python 3.11 slim，启动 `uvicorn branch_agent.app:create_app --factory`，并使用内嵌 worker。已有腾讯云测试实例的仓库目录据 `README.md` 为 `/opt/nex-branch-agent`；**本仓库没有完整的自动部署脚本、Nginx 配置、经验证的 SSH 地址/密钥映射或自动回滚脚本**，先在服务器核对实际环境，不要臆造一条可以直接执行的远端命令。

1. 本地完成修改与上述测试，更新 `branch_agent/static/release-notes.json`，检查 `git status` 和差异，提交后推送 `origin/main`。先确认新改动是否属于当前工作区，别把开发者的 `.env`、数据、测试临时文件纳入提交。
2. 登录服务器核对 `/opt/nex-branch-agent` 的远端、当前 commit、`compose.yaml`、Nginx 反代与已有 `.env`。服务器至少需要 `BRANCH_DB_PASSWORD`、`DEEPSEEK_API_KEY`、`BRANCH_LOCAL_PASSWORD`；OpenAI 模型另需 `OPENAI_API_KEY`。这些值保留在服务器，不写入仓库或交接文档。
3. 安排维护窗口，停止新写入并处理正在运行的 worker/模型调用；不要在两个卷持续写入时分别取互不一致的快照。**对同一逻辑时点备份数据库和 `/data` 文件卷，并验证备份可读**；记录部署前 commit 与数据库迁移版本。数据库可用类似 `docker compose exec -T database pg_dump -U branch_agent -d branch_agent -Fc > <安全备份路径>.dump` 的方式；文件卷按服务器实际卷名备份。不要执行 `docker compose down -v`，它会删除持久卷。迁移随应用启动自动执行，旧数据库状态无法仅靠切回 Git commit 保证回滚。
4. 将已测试的**明确 commit**拉到服务器仓库，在目标目录执行 `docker compose up -d --build`。确认 `docker compose ps` 和应用/数据库日志无错误；在服务器上访问 `http://127.0.0.1:8767/health` 与 `/api/branch-agent/v1/release`，再从调试同学使用的公网 HTTPS 地址测试登录、创建小项目、查看配置和产物。重建若中断外部模型调用，检查暂停及 `operation_uncertain` 状态，勿自动重发不确定的请求。必要时核对 Nginx 与防火墙规则，但不要在没有现场证据时改它们。
5. 记录部署 commit、时间、迁移结果、健康检查和可用的备份路径。若失败，先保存日志与数据库/文件状态，再依据备份制定回退；本仓库没有经过验证的一键回滚。GitHub 推送和腾讯云部署是两个独立步骤，分别核对结果。

## 8. 建议接手顺序和当前待核对项

1. 先读本文件、`README.md`、`branch_agent/engine.py`、`step1_execution.py`、`workflow.py`、`manager.py`、`model_service.py`；再读 `docs/context/stage-materials.json` 与 Schema registry。Step1 的两路执行在 `step1_execution.py`，Step2 的单一知识资产由 `engine.py` 按阶段通用候选产物流程保存和确认，阶段映射见 `workflow.py`。
2. 先 `git status` 核对工作区，再在自己修改后重跑完整测试。当前离线回归结果见第 0 节；真实模型联调仍待做。重点检查自适应窗口预算在全局分析累计、人物历史摘要、不同模型、极短窗口和恢复任务下是否稳定。
3. 用短篇与超过阈值的原文分别验证：两路确实并行；三份产物固定同一原作版本；人物事件不依赖全局事件且没有逐事件原文索引；窗口完整覆盖；Step2 发生一次知识资产分析模型调用并只询问一次；确认后 Step3 能读取知识资产。重点检查每路失败后另一分支进度、前端最新产物显示和配置发布后的 Run 快照。
4. 如果继续用户提出的上下文压缩重构，先以 `docs/context/上下文压缩策略开发方案.md` 作为需求记录，与 `compaction.py` 当前实现逐条对照。`web_search` 的搜索结果会进入调用它的 Agent Session 和工具审计，继续保持结果条数与文本长度上限；它不是上下文压缩工具。
5. 推送与部署前核对回归、真实模型联调和目标环境的版本；部署时保留云端 `.env`、数据库、项目记录和配置，除非用户另有明确授权。
