## 1. 上下文与 Session 管理

### 1.1 目标与原则

Harness 必须保存项目内全部用户对话、版本化产物及关键决策，支持跨阶段追问、任务恢复和来源检索。每次模型调用只加载当前任务所需的有效材料；Step1 切分、修正和重试始终同时加载固定版本的完整原文。工作 Session 可裁剪、压缩或重建，原始归档独立保留；不得以摘要或片段替代 Step1 的原文。历史回答只能依据已有记录，缺少理由时不得补造。

项目对话的连续性由归档与检索保障。Session 划分不决定 Agent 数量或业务步骤的执行顺序。

### 1.2 数据与上下文边界

| 对象 | 职责 | 模型可见方式 |
| --- | --- | --- |
| 运行时 `context` | 向工具、Hooks 等传递项目 ID、存储服务、当前阶段等应用依赖 | 经输入、动态 instructions 或工具返回值显式提供 |
| SDK `Session` | 跨运行读取、保存消息、工具调用和工具结果等 items | 由 `Runner` 加载，并受历史读取与输入处理策略限制 |
| 本次模型上下文 | 本次调用的 instructions、历史、当前请求、工具定义及相关材料 | 受模型上下文窗口限制 |
| 原始交互归档 | 保存真实对话、确认、纠正、撤回及执行记录 | 按问题检索、读取 |
| 业务产物与决策记录 | 保存原作切片、方案、章节设计、Graph，以及选用／否定方案的明确记录 | 按任务、范围和固定版本加载 |

持久保存与模型输入分别管理。Harness 从持久记录中选择相关且有效的内容，不自动拼接全部历史。

### 1.3 存储与检索结构

系统部署在服务端，复用工具平台的账号体系。对话、产物版本、决策、确认和任务进度由服务端持久保存并关联账号与项目；同一账号重新登录或更换设备后，可以读取此前有权访问的项目、会话历史及最新任务状态。浏览器缓存不作为唯一记录来源。

用户可见的会话与 Agent 内部工作 Session 通过稳定引用关联，平台登录会话单独管理。工作 Session 的裁剪、压缩或重建不影响原始历史展示；退出登录不删除项目数据，也不触发任务停止。后台执行与恢复遵守 4.2。

系统包含三个独立的逻辑记录域，通过稳定消息 ID、产物版本和任务引用关联：

1. **项目对话与原始归档**：保存项目内所有人工交互，包括阶段或章节内部的讨论、否定、确认和修正，以及子任务与工具执行记录。
2. **阶段／章节工作 Session**：保存同一任务的连续工作历史，支持结束、归档、裁剪和压缩；其他工作范围不默认继承其全部执行历史。
3. **可检索项目材料**：保存版本化产物、关键决策、原文定位及其引用关系，供生产、历史查询和恢复使用。

原始归档必须独立于可压缩、清理的工作 Session。物理存储可共用数据库，文件型产物通过持久引用关联。所有检索必须限定 `project_id`，并支持进一步限定阶段、章节和版本；跨 Session 检索由 Harness 实现。

首版使用 PostgreSQL 保存结构化记录及内联 JSON，大内容通过 Blob 引用服务端持久文件存储。准确记录 Schema、关系约束、读写接口及同页可视化见第 10 节。

### 1.4 Session 划分与调度

围绕同一项需要连续讨论的任务组织工作 Session。阶段编号变化、切换 Agent 或完成一次输出，不自动更换 Session。

| 阶段 | 工作 Session | 跨阶段保存的内容 |
| --- | --- | --- |
| Step1：原作双视图切片 | 独立 | 原文版本、全局事件视图、主要人物事件视图、UTF-16 原文位置索引、用户对切片标准的修正 |
| Step2：原作核心信息分析 | 与 Step3、Step4 共享“改编方向”Session | 分别保存全局事件分析与主要人物事件分析，以及各自的版本和确认记录 |
| Step3：确认玩家角色与互动策略 | 与 Step2、Step4 共享 | 玩家身份、用户想法、策略变化、被否定方案及已记录理由 |
| Step4：推导改编方案 | 与 Step2、Step3 共享；方案稳定后保存检查点 | 改编方案版本、依据、确认状态 |
| Step5：游戏层面的事件视图 | 与 Step6 共享“宏观互动结构”Session | 已确认的游戏事件视图及写回改编方案的版本 |
| Step6：事件叙事功能／玩家意图单元 | 与 Step5 共享 | 事件叙事功能、用户修正与确认、写回方案的版本 |
| Step7：结局与大概路线 | 独立“结局路线”Session | 结局与路线、用户确认、写回方案的版本 |
| Step8：目标玩家画像 | 独立“玩家画像”Session | 玩家画像、用户确认、写回方案的版本 |
| Step9：章节互动设计 | 每章独立 | 章节事件组成、完整线性正文、互动设计、用户确认、依赖的方案版本 |
| Step10：章节互动剧本生成 | 每章独立于 Step9 的生成 Session | 分支正文、Nexo Graph、用户修改与确认、依赖的章节设计版本 |
| Step11：审核 | 独立 | 被审核版本、审核标准与证据、全局变量／互动设计检查结果、问题依据和修复记录 |

- 不同工作范围通过有效产物、相关决策和历史检索衔接，不整段复制历史。Step5、Step6 共用宏观互动结构 Session；Step7、Step8 各用独立 Session，并分别只读取方案所引固定版本的阶段产物。返回前一步修改产物按工作流与确认规则执行，不因共享 Session 自动重跑。
- Step7 的候选探索留在结局路线 Session；来源版本由 Harness 固定，确认结果写回方案。子任务是否采用子 Agent 与 Session 划分分别配置。
- 进入另一章节、独立任务、并行探索，或重大上游改版使原工作假设失效时，新建或切换 Session。同一任务仅因上下文增长时优先裁剪或压缩；小幅修改在原 Session 中记录版本变化。
- 章节 Session 支持暂停与恢复，恢复前检查依赖版本。同一 Session 的写入串行执行；并行章节使用不同 Session，并分别固定公共方案版本。
- 对话协调 Agent 使用项目级协调工作 Session，保存近期用户对话、项目概况和当前事项，不汇入所有专业 Agent 的执行历史。该 Session 按本节规则压缩，并通过消息、产物和任务引用关联阶段 Session；职责见第 5 节。

### 1.5 持久化记录与版本规则

#### 1.5.1 最小保存内容

| 记录 | 必须保存的信息 |
| --- | --- |
| 项目与会话索引 | 平台账号归属、项目 ID、用户可见会话 ID 与标题、创建／更新时间、内部工作 Session 引用 |
| 原始交互 | 消息 ID、项目 ID、用户可见会话引用、发言方、时间、原始内容、阶段／章节、相关产物版本 |
| 原作与产物 | 稳定 ID、类型、版本、内容或文件引用、状态、来源引用、依赖产物版本 |
| 决策 | 决策 ID、讨论事项、选定／否定结果、明确表达的理由、来源消息、确认状态、适用版本、替代关系 |
| 工作 Session | Session ID、项目 ID、阶段／章节、关联运行 ID、输入版本、工作状态 |
| 工作摘要 | 摘要 ID 与版本、项目及 Session ID、覆盖的历史消息、引用的产物版本、结构化内容、校验状态 |
| 调用依据 | 运行／调用 ID、配置版本、提示词版本、实际加载的产物版本和消息引用、材料选取及省略原因、token 估算 |

归档范围包括用户与 Agent 的全部原始对话、阶段及子任务的实际交互与输出、候选方案和未采用结果、修改过程，以及工具名、调用参数、结果与错误。通过 Session、阶段、子任务和调用 ID 关联记录。大段原文、Graph 等内容独立持久化并固定版本引用。

当前运行仍需使用的工具结果进入后续模型调用；已结束任务的历史按需检索。归档保存实际可获得的交互与执行记录，不依赖模型内部思维链。需要决策依据时，显式生成简短说明并关联证据与确认记录。

#### 1.5.2 决策与确认

玩家身份、原作保留要求、禁止结局等影响后续生成的选择单独保存为决策；普通措辞修改保存在对话和产物版本中。决策必须区分“用户提出”“Agent 建议”“用户确认”；未记录的理由标为“未记录”，不得用后续分析补写为历史事实。

确认采用“明确表态即确认，含糊时再询问”：

- 用户明确指定选择或要求按某方案执行时，关联原始消息并确认对应内容，无须额外点击或重复确认。
- 试探性表达保留为讨论；用户沉默不构成确认。
- “可以，就这样”等表态仅在指代对象和范围明确时生效；无法确定时询问用户，并保持原有有效决策。
- 确认仅作用于用户明确认可的内容，不扩大到其他字段或整份方案。

#### 1.5.3 产物单位与版本

| 产物 | 保存单位与依赖 |
| --- | --- |
| 原作切片、分析、策略、事件视图、路线、玩家画像 | 各阶段分别保存，具有独立 ID 和版本 |
| 互动改编方案 | 汇总相关阶段结果，固定引用各结果的具体版本 |
| 章节互动设计 | 每章独立保存和管理版本，关联改编方案版本 |
| 章节剧本／Graph | 每章独立保存和管理版本，关联章节设计版本与项目基线快照；整剧 `nexo_graph` 独立保存组装结果及所用章节版本 |
| 审核报告 | 每次审核单独保存，关联被审核的产物版本 |

独立保存指逻辑记录单位，不要求独立文件或数据库。所有依赖指向确定版本，上游更新不改写历史依赖。产物至少区分草稿、已确认、已被替代，并独立标记依赖有效性；当前有效版本按生效规则确定。

| 事件 | 版本处理 |
| --- | --- |
| Agent 完成产物生成或修改 | 保存新草稿版本，保留旧版 |
| 用户直接编辑并保存 | 内容变化时保存新版本 |
| 用户确认某版本或其中部分内容 | 保存关联该版本的确认记录及范围，不重复生成内容版本 |
| 流式生成片段、失败调用 | 保存执行历史，不逐片段建立产物版本 |

新草稿不自动取代已确认结果。确认记录与内容版本分别管理，旧版本及确认依据持续保留。

### 1.6 运行上下文组装

Harness 按任务类型和阶段配置自动读取必需材料；Agent 通过第 2 节工具补充材料。配置及默认数值见第 3 节。

具体执行采用[上下文执行方案](context/上下文执行方案.md)；[阶段材料配置](context/stage-materials.json)规定来源、字段、范围、加载方式和覆盖要求，[默认参数](context/defaults.json)规定 Step1 全文准入上限及其他阶段的分批初值。各项配置进入同页 HTML 配置区及运行快照。

#### 1.6.1 组装流程与固定输入

1. 解析项目、阶段、章节／分支、任务类型及目标；影响材料选择的对象不明确时先定位。
2. 固定配置快照和必需产物版本，检查状态与依赖有效性。
3. 按全局、项目、Agent／阶段及辅助任务配置组合 instructions；原作、历史、产物和检索内容作为有来源标记的数据加载。
4. 加载适用约束、阶段必需产物、当前摘要、近期完整交互及当前运行所需工具结果。
5. 历史追问检索来源；普通生产先读取直接依赖，再按需补充证据。
6. 处理范围与版本冲突，去重并检查预算，记录输入清单后调用模型。

每次调用必须包含以下输入，已有有效内容不重复追加：

| 输入部分 | 内容 |
| --- | --- |
| 任务信息 | 当前用户请求、目标、项目／阶段／章节／分支范围、产物状态 |
| 执行要求 | 生效的 instructions、输出格式、可用工具定义 |
| 适用约束 | 相关有效决策、禁止事项、保留要求及来源；分支条件的适用范围 |
| 直接材料 | 本阶段及子任务必需的产物字段、原文片段、版本和依赖引用 |
| 工作连续性 | 有效工作摘要、预算内最近完整交互、当前运行尚需使用的工具结果 |

必需来源必须读取并校验。Step1 使用全文输入，每次切分、修正和重试均同时加载固定版本的完整原文；不得摘要替代、裁剪原文、串行分页累积阅读或自动分批。其他阶段可按固定版本分批展开，记录已处理／未处理范围；要求全量覆盖的任务不得仅凭总览报告完成。

Step1 原文导入上限默认 `context.step1_source.max_source_tokens=200000`，阶段总输入上限 256000、输出上限及预留 32000、安全余量 2000 tokens。输出上限包含推理与可见输出。按所选模型适配层计量并保留 tokenizer／估算器版本；原文上限是项目准入限制，不是模型能力值。启动前和每次模型调用前同时检查原文 token 数不超过该上限，且完整原文、instructions、必要材料、输出／工具协议和当前必要交互的总输入不超过可用预算 `B`，输出另行预留。超限时拒绝启动或暂停后续调用，展示计量与阻塞原因；调整有效配置／受支持模型，或由用户明确提供新的完整较短作品版本后重新检查。不自动截短作品。

#### 1.6.2 各阶段默认材料

| 阶段 | 自动读取的必需来源与工作材料 | 按需补充材料 |
| --- | --- | --- |
| Step1：原作切片 | 同时加载固定版本的完整原文、目录／范围索引、切片规则及用户修正；修改时加入既有双视图和待修正问题 | 切片标准的历史讨论及既有结果依据；不得以补充读取代替全文加载 |
| Step2：核心信息分析 | Step1 双视图、原文来源索引、本批事件与相关人物信息 | 待核对原文、跨事件因果和人物记录 |
| Step3：玩家身份与互动策略 | 全局事件分析、主要人物事件分析及各自确认状态、默认策略、用户当前互动想法 | 原作双视图、对应原文与过去讨论 |
| Step4：改编方案 | 全局事件分析、主要人物事件分析、已确定的玩家身份与策略、适用保留要求和禁止事项 | 原作事件、人物细节、决策出处 |
| Step5：游戏事件视图 | 原作全局事件视图、主要人物事件视图、全局事件分析、主要人物事件分析及本次改编范围详细事件 | 原文、其他角色视图、相关历史理由；Step4 方案只作为 Harness 写回目标，不进入模型上下文 |
| Step6：叙事功能／玩家意图单元 | Step5 `interactive_structure` Session 的交互与工具结果，Harness 固定的 Step5 双视图、两份分析和游戏事件输出，以及本阶段 instructions | 模型只返回事件 ID 与叙事功能；Harness 校验每个现有事件恰好一项，按原事件顺序合并并保存新版本 |
| Step7：结局与路线 | Harness 从 `adaptation_plan.stage_artifact_refs.game_events` 解引用的固定版本事件视图（每个事件已含 `narrative_function`）及本阶段 instructions | 不自动加入方案全文、Step5–6 历史或其他材料 |
| Step8：玩家画像 | Harness 从方案解引用的固定版本含叙事功能事件视图与已确认结局路线，以及本阶段 instructions | 不自动加入方案全文、Step5–7 历史或其他材料 |
| Step9：章节互动设计 | 固定版本的 `adaptation_plan`、Harness 从方案引用解出的完整 `game_event_view`（含叙事功能）、`ending_routes`、`player_profiles`、本章固定原作正文及 Step9 instructions。缺少可靠章节锚点时使用固定原作全文 | 本阶段不自动加入其他章节设计或额外产物 |
| Step10：章节剧本／Graph | 本章已确认的完整 `chapter_design`、由其 `chapter_source_anchors` 精确提取的对应原作正文，以及 Step10 instructions | 无额外模型材料；Graph 基线、身份与版本由 Harness 内部处理 |
| Step11：审核 | 被审核版本清单、审核标准、全局变量与 Graph 结构、本批章节内容和约束；记录全剧覆盖范围 | 原作核对片段、决策来源、生成与修复历史 |

材料读取遵守实际确认范围和阶段生效规则，缺少有效输入时不得把草稿提升为有效产物。配置调整必需来源时，必须检查下游内容仍有来源；改为按需读取的必需内容，仍须在对应子任务执行前读取并校验。Step1 原文固定为自动、完整、必需加载，不允许通过字段配置改为引用、索引、片段或按需读取。

#### 1.6.3 按任务选择材料

| 任务类型 | 组装规则 |
| --- | --- |
| 生产 | 自动读取对应阶段来源并固定依赖版本，再补充细节 |
| 当前结果查询 | 读取目标的当前有效结果与确认范围 |
| 历史追问 | 检索相关决策和记录，读取原始出处与当时版本 |
| 修改 | 加载被修改版本、新要求、相关约束和影响范围；新内容保存为草稿 |
| 恢复 | 校验摘要和依赖版本，加载未完成事项、近期交互及材料；过期摘要仅用于历史定位 |

默认保留最近 6 个已完成用户交互回合，并受近期历史 token 预算限制。一个回合包含用户输入及其后相关助手／工具交互；当前未完成交互单独保留，不受 6 回合数量限制。更早内容通过摘要和检索补充。

摘要与原始消息按来源 ID 去重；需要展开原话时省略对应重复摘要。产物片段按产物 ID、版本和范围去重，保留版本标记。

#### 1.6.4 冲突与缺失

- 当前业务事实以适用范围内的有效决策和正式产物为准，摘要与旧对话不得覆盖。
- 当前明确变更按确认规则登记范围与来源，并标识依赖旧决定的产物；修改完成前，不将新决定和旧产物视为一致的有效方案。
- 有效决定在同一范围内冲突、表态含糊或分支范围不明时，暂停依赖该结论的生成并询问用户；历史查询可继续陈述记录。
- 原作事实、改编设定、分支事件、角色所知和变量条件分别标识，不混为全局事实。
- 必需来源缺失或读取失败时停止依赖它的生成；可选材料缺失时记录缺失并继续无依赖工作。搜索未命中与读取失败按第 2 节分别处理。

#### 1.6.5 预算缩减顺序

统计 instructions、工具定义、历史、材料和当前输入的总量。超过压缩触发阈值时依次执行：

1. 去重；移出无关旧工具输出和未采用候选详情，保留检索引用。
2. 减少可选检索结果及邻近内容，保留直接相关证据。
3. 将较早完整交互转为有出处的摘要，保留当前请求和必要交互链。
4. 除 Step1 外，将过大必需产物拆为子任务所需字段／片段，其余按固定版本分批读取。
5. 仍无法容纳必需材料时，其他阶段拆分任务或调整预算；Step1 拒绝超限调用并等待解决准入限制，不拆分原文。不静默省略约束、确认范围、输出协议和关键证据。

Step1 的完整原文是每次调用的必需材料，不参与裁剪、摘要或批次替换。可清理无关历史，但不得为达到压缩目标而减小全文输入；超过 `B` 时按全文准入规则处理。

每次模型调用记录来源 ID、实际版本、读取范围、加载原因、token 估算及省略内容与原因，供回溯及 HTML 上下文预览使用。

### 1.7 历史查询

历史查询限定当前项目，支持跨阶段、跨 Session。已知目标产物时直接读取；否则先搜索简短片段和稳定引用，再按需展开原文、附近对话及当时版本，大内容分页读取。

- 历史原因必须关联当时的决策或原始讨论。只有结果而无理由时，明确说明未找到理由；新的分析单独标识。
- 区分用户试探性想法、Agent 建议和明确决定；摘要不得作为原话的唯一依据。
- 未命中时按事项、阶段和版本扩大项目内检索；仍缺乏依据时说明记录不足，不断言用户从未说过。
- 所有返回保留出处、实际版本和状态。查询历史或修改影响不触发产物覆盖、上游重跑或确认推进。

### 1.8 上游变化与依赖有效性

稳定条目身份、字段迁移、依赖影响与确认继承按[版本与确认映射](context/版本与确认映射.md)执行。历史引用保持固定；只有身份、内容、顺序语义及依赖都验证未变的范围可继承旧确认，新增或改写范围遵守原阶段确认规则。原作正文改版后，Step1 必须基于新版本全文重新检查双视图的全本切分，不能只处理改动片段；下游已完整证明内容、语义保护范围和依赖未变的结果仍可保留。

Step5～Step8 的确认结果写回互动改编方案，生成新版本。后续阶段固定读取方案版本，并执行以下规则：

- 确认关联具体版本，旧版确认不自动适用于新版。
- 用户撤回或修改决定时追加变更记录，保留原决定及适用范围。
- 派生产物固定记录输入版本；上游修改后，将可能受影响的下游产物标为“需复核”，再判定重做范围。
- 继续旧 Session 前检查依赖变化；需要时更新上下文或新建 Session，不沿用过期约束。

### 1.9 上下文裁剪与摘要

采用“按需读取 + 阶段检查点 + 预算触发摘要”。业务检查点、摘要内容、触发策略和安全替换由 Harness 实现；原始归档不随工作历史压缩删除。

#### 1.9.1 触发时机

| 时机 | 动作 |
| --- | --- |
| 每次模型调用前 | 估算输入、去重、限制检索与工具输出；Step1 加载完整原文并检查准入，其他阶段加载所需范围 |
| 关键人工确认或阶段完成后 | 保存产物／决策版本并更新检查点；不要求每次调用模型压缩 |
| 下一次调用接近预算 | 在安全边界以摘要替换较早工作历史，保留必要材料和近期完整交互 |
| 切换范围或重大上游改版 | 由有效产物、决策与未完成事项组装新上下文；旧 Session 仍可检索 |

安全边界要求相关记录已持久化、成对工具交互已完整。工作历史的持久替换不得与同一 Session 的运行写入并发；运行内也必须限制工具返回量并逐次检查输入。

#### 1.9.2 预算与阈值

可用输入预算 `B = min(解析后的阶段 context.input_token_cap, 模型上下文窗口 − model.max_output_tokens − context.safety_margin_tokens)`。各配置值先按继承规则解析；输出预留等于当次输出上限，包含推理与可见输出。输入估算包括完整原文或所需材料、instructions、输出／工具协议、历史和当前消息。

默认预计输入超过 `75% × B` 时先去重和缩小检索范围；仍超阈值且存在可压缩旧工作历史时生成摘要，目标约为 `50% × B`。两项比例均可配置。Step1 必需全文保留；若不可裁剪的必要输入已高于软阈值但仍在 `B` 内，直接保留并继续，不为达到比例目标反复压缩。

压缩后重新估算。其他阶段必需材料超预算时分块读取或拆分任务，不反复压缩同一摘要。Step1 完整原文不压缩、不分块；当全文与必要输入已高于压缩目标但仍不超过 `B` 时允许调用，不为追求目标比例删减全文。实际总输入仍超过 `B` 时保留原记录并拒绝调用，按全文准入规则解决。

#### 1.9.3 摘要内容与版本

| 内容 | 处理规则 |
| --- | --- |
| 已确认约束、禁止事项、产物状态与版本 | 直接加载正式记录 |
| 目标、进度、未解决问题、修改请求 | 保留工作状态，区分已确认与待讨论 |
| 角色动机、伏笔、事件因果、变量与分支条件 | 保留任务必需内容、范围和来源 |
| 近期讨论与必要工具交互 | 预算内优先完整保留，保持交互链有效 |
| 较早讨论与探索 | 摘要保留结论、已记录理由、否定／撤回事项及出处；原文留在归档 |
| 大段原文、完整 Graph、重复候选与日志 | 持久保存，其他阶段当前输入只带相关片段、必要结果和固定引用；Step1 始终保留完整原文 |

工作摘要是 Harness 内部纯文本压缩产物，不注册为 Agent `output_type`。模型只整理已有历史；程序记录覆盖消息、来源引用、Session 代次和产物版本。

每个工作 Session 独立维护当前摘要；Step2～Step4、Step5／Step6、独立的 Step7、独立的 Step8 及各章节分别管理。压缩或恢复时按需生成、更新；每次保存新摘要版本、覆盖消息范围和引用版本，并保留旧版。摘要自动校验，通过后更新当前引用，无须逐次人工确认；失败时保留原摘要与历史。

摘要只整理已有信息，不确认决策或改变产物状态。更新时结合结构化记录及必要原文校准，不持续仅对上一版摘要再次概括；正式产物、原始讨论和确认记录仍分别读取。

#### 1.9.4 安全替换与实现边界

执行顺序：原始交互归档 → 读取有效状态 → 生成并校验摘要 → 记录覆盖消息与版本 → 安全替换工作历史 → 检查下一次输入协议与预算。任一步检查失败时保留旧工作历史；新建 Session 时保留原记录关联。历史追问仍按 1.7 读取归档。

- item 数量限制不能替代 token 预算，裁剪必须保持工具调用与结果配对。
- 清理前确认原始消息、决策和产物已持久化；归档失败不得删除唯一副本。
- 使用可审阅的纯文本工作摘要，初始版本不接入 `OpenAIResponsesCompactionSession`，也不叠加原生 compaction。
- 替换压缩实现时验证模型／接口支持及信息保留效果，并继续独立保存原始归档、业务检查点、版本和检索引用。

### 1.10 Agents SDK 适配边界

SDK 适配版本为 `openai-agents==0.22.2`，升级时执行适配回归。

| SDK 接口 | 使用要求 |
| --- | --- |
| `Runner.run(..., context=...)` | 传递运行时依赖；模型输入与项目记忆另外组装、保存 |
| `Runner.run(..., session=...)` | 读写运行历史；Session 路由、跨 Session 检索和业务版本由 Harness 管理 |
| SDK Session 存储适配 | 服务端使用第 10 节 PostgreSQL 工作历史实现 Session 读写协议；`SQLiteSession` 可用于本地 SDK 学习，不作为服务端项目历史的存储方案 |
| `Session.get_items`、`add_items`、`pop_item`、`clear_session` | 读写工作历史；项目检索、产物版本和决策另建记录 |
| `SessionSettings(limit=...)` | 仅限制读取 item 数量，不删除旧记录或生成摘要；token 预算由 Harness 管理 |
| `RunConfig.call_model_input_filter` | 逐次检查和调整模型输入；材料选择、预算与归档分别实现 |
| `OpenAIResponsesCompactionSession` | 初始版本不接入，替换实现遵守 1.9.4 |

Harness 负责项目归档、产物版本、决策出处、跨阶段检索和依赖有效性。运行状态另行持久化，恢复 Session 历史不等于恢复审批暂停点或整个流程。

### 1.11 实现范围与验收

实现持久化归档、工作 Session、版本化产物、带出处的决策、按范围读取工具、结构化摘要和预算控制。历史查询使用明确 ID、字段过滤和全文检索；语义检索根据查询效果扩展。

| 验收场景 | 预期行为 |
| --- | --- |
| 在 Step10 追问 Step3 的角色选择 | 找回当时决策、来源消息和具体版本；缺少理由时如实说明 |
| Session 已压缩或重建 | 独立归档仍可读取原始讨论及确认依据 |
| 输入接近预算且含大段工具输出 | 缩减输入、按需压缩，下一次调用满足预算且工具交互完整 |
| 摘要错误确认待讨论内容或引用不存在 | 拒绝替换工作历史，不修改正式确认 |
| 归档或摘要生成失败 | 保留旧记录，不删除唯一副本，不发送已知超限请求 |
| 同一账号换设备或重新登录 | 读取原有会话、产物、确认与服务端最新进度 |
| 关闭页面或退出登录 | 已启动任务在授权范围内继续，直到完成、等待用户或遇到需处理的异常 |
| 服务端重启或异常中断 | 按 4.2.2 核对检查点后自动恢复可恢复任务；已完成结果不重复写入 |
| 待用户输入、收到停止请求或已主动停止 | 服务恢复后保持对应等待／停止意图，不自动恢复执行 |
| 查询 Step1 分段及切片标准修正 | 读取切片产物、UTF-16 原文索引及用户修正记录 |
| 生成未确认草稿 | 与当前已确认结果分开管理 |
| 用户修改已确认上游方案 | 保留旧版及变更出处，标识依赖旧版的下游产物需复核 |
| 并行处理不同章节 | Session 隔离，各自读取正确章节材料与公共约束版本 |
| 仅查询历史或修改影响 | 不覆盖产物、重跑或推进确认 |
| 同时存在多个账号与项目 | 历史、产物、Session 与任务查询同时执行账号权限及项目归属检查 |

## 2. Tool 与内部接口

### 2.1 职责与工具清单

Agent 工具提供主动读取能力，Harness 内部接口负责自动记录、校验与持久化。以下三个项目自定义工具均为只读；确定的阶段依赖由 Harness 自动读取，两种方式共用版本解析、项目范围和来源引用规则。

| 工具 | 职责 |
| --- | --- |
| `get_artifact` | 读取业务产物的当前有效结果、最新草稿或指定历史版本 |
| `search_records` | 定位对话、决策、产物、摘要及执行记录 |
| `read_record` | 展开固定记录、原文、来源及必要邻近内容 |

原作固定版本及片段登记为 `read_record` 可读来源。UTF-16 原文位置核验、Graph 格式与引用检查、完整章节快照变更比对及整剧组装由 Harness 自动执行，并向对应 Agent 返回有来源的结果。Agent 工具配置见第 5 节。

`get_artifact` 读取 Graph 时返回第 6 节定义的 `Project` 结构及独立版本元数据。其他业务工具在对应模块中定义，并登记功能、输入、返回和操作边界。

### 2.2 读取契约

#### 2.2.1 `get_artifact`

| 项目 | 定义 |
| --- | --- |
| 目标 | 产物 ID，或可唯一定位产物的类型与阶段／章节范围 |
| 版本 | 默认 `current_effective`；可指定 `latest_draft` 或具体版本 |
| 范围 | 内容片段；大产物支持分页游标 |
| 返回 | 产物 ID、实际版本、内容或片段、产物状态、确认范围、依赖版本及有效性、来源引用、分页信息 |

- 当前有效结果按阶段生效规则和确认范围解析，不按最新生成时间选择。
- 请求范围无有效结果时返回 `no_effective_version`，不自动回退草稿。
- 部分确认返回明确范围，不将整份标为已确认，不静默拼接多个版本并标为单一版本。
- 草稿和历史版本保留真实状态；依赖失效时标记“需复核”。
- 目标不唯一时返回 `ambiguous_target` 及候选标识，由调用方进一步定位。

#### 2.2.2 `search_records`

| 项目 | 定义 |
| --- | --- |
| 查询 | 文本，以及可选的记录类型、阶段、章节、Session、时间范围、版本或状态筛选 |
| 结果控制 | 数量上限、分页游标；Harness 同时限制返回内容大小 |
| 返回 | 简短片段、记录类型、稳定引用 `record_ref`、时间、阶段／章节／Session、实际版本与状态、原始来源引用、分页信息 |

- 可检索原始对话、决策、产物、摘要及阶段／工具执行记录；默认包含未采用、被否定和已被替代记录，除非显式筛选状态。
- 使用字段过滤与全文检索，无匹配返回 `no_matches`；可调整关键词或放宽当前项目内筛选继续检索。
- 命中摘要时标明类型并提供原始出处，不能将摘要作为用户原话的唯一证明。
- 仅返回定位片段，详细原文通过 `read_record` 读取。

#### 2.2.3 `read_record`

| 项目 | 定义 |
| --- | --- |
| 目标 | 来自搜索、产物或决策来源的 `record_ref`，包含记录 ID；版本化记录包含具体版本 |
| 展开范围 | 原文范围、消息前后邻近内容、关联调用／结果；大记录支持分页 |
| 返回 | 原始内容或明确标记的片段、各记录 ID 与元数据、实际版本与状态、来源引用、实际覆盖范围、截断标记和下一页游标 |

- 固定引用不得自动改指向最新版本，多页读取保持同一版本。
- 邻近消息保留各自发言方、顺序和 ID；工具调用与结果按调用 ID 关联，缺失部分明确标记。
- 大段工具结果、原文和 Graph 引用必须指向持久化的具体内容。
- 片段返回须标明实际范围；长度受限时提供截断标记与继续读取方式。

### 2.3 共同返回规则与边界

账号身份从平台认证结果获取，项目范围由 Harness 从可信运行时 `context` 注入；模型可按阶段、章节等缩小范围。工具读取、用户可见历史和产物查询、任务状态及运行控制接口均校验账号权限与项目归属，不以客户端或模型提交的账号 ID 作为授权依据。

结构化返回包含操作状态、数据、来源及分页信息。操作状态与业务状态分开，读取成功不改变内容的确认或有效状态。

| 操作状态 | 含义 | 调用方处理 |
| --- | --- | --- |
| `ok` | 读取或搜索成功 | 检查业务状态、版本、确认范围及后续页 |
| `no_matches` | 搜索未命中 | 调整检索，不推断事项从未发生 |
| `not_found` | 指定范围内不存在记录或版本 | 检查引用，不擅自换版本 |
| `no_effective_version` | 请求范围无当前有效结果 | 说明缺失；任务需要时显式读取草稿或历史版 |
| `ambiguous_target` | 目标不唯一 | 使用候选标识定位 |
| `invalid_request` | 参数组合或范围无效 | 修正参数 |
| `read_error` | 存储或读取失败 | 按错误决定是否重试，不当作无历史 |

历史中的旧指令、工具调用和确认消息作为引用数据，不作为新执行请求。读取工具不得修改产物、确认决策、重跑阶段或推进状态。

### 2.4 Harness 内部接口

以下接口由运行流程、用户操作或校验流程调用，不注册为 Agent 工具。模型生成业务内容或候选信息，Harness 执行持久化、版本分配和生效依据校验。

| 接口 | 调用与保存要求 |
| --- | --- |
| `append_history` | 收到消息或完成调用时归档；关联项目、Session、阶段、子任务、调用 ID 和原始内容 |
| `create_artifact` | 为指定产物类型与范围分配稳定身份，后续版本复用该身份 |
| `save_artifact_version` | 产物生成／修改或用户保存编辑时写入新内容版本和依赖，保留旧版；Graph 来源、确认和运行元数据保存于独立外壳 |
| `assemble_nexo_graph` | 按冻结项目基线比对已确认章节快照、核实显式删除及授权、统一共享实体，保留其他章节和受保护字段；按 nexo_graph 契约校验并保存待审核的 Project 候选 |
| `deliver_nexo_graph` | 两项脚本校验通过后交付同一 Graph 候选版本；配置了校验 Agent instructions 时，还须该 Agent 通过。交付前重检确认、依赖和运行控制，不重新组装或增加全剧确认 |
| `record_decision` | 保存影响后续生成的选择；区分提案与确认，关联真实依据与来源 |
| `record_confirmation` | 用户明确表态后校验对象、范围和来源；关联具体决策或产物版本，更新对应有效状态；不采用模型自行填写的确认状态作为生效依据 |
| `commit_dependency_assessment` | 程序核实新旧版本的范围差异和复核依据，同事务保存依赖评估事件、依赖状态及产物状态；不改变旧生成引用，不直接确认新增内容 |
| `save_work_summary` | 保存纯文本摘要及程序确定的覆盖范围与来源引用，更新 Session 当前引用，保留旧版 |
| `steer_run` | 保存消息并校验目标运行，在执行边界纳入要求，记录实际纳入位置，按第 4 节检查依赖 |
| `enqueue_request` | 持久保存原消息、任务范围和队列状态；执行前重组上下文并校验版本 |
| `interrupt_run` | 请求取消指定运行，阻止继续调度新工作，记录实际停止情况与未完成操作，不回滚已完成写入 |
| `interrupt_task` | 停止指定业务 Task 及其子树；无活动 Run 的等待任务也可停止 |
| `resume_task` | 接收明确继续操作，核对暂停原因、检查点、依赖与预算后恢复；累计用量保留 |
| `resume_queue` | 接收明确继续排队处理的操作，解除对应会话的队列 hold；不恢复旧任务或绕过其预算与依赖 |

自然语言确认可由模型提出候选对象与范围；含糊时继续询问用户。所有保存结果必须能通过稳定引用再次读取。

上述内部接口的准确输入、返回、错误、幂等与事务约束见 [Harness 存储与接口契约](harness-data/storage-and-api.md)。记录字段以 [records.schema.json](harness-data/records.schema.json) 为准。

最终 Graph 使用两阶段处理：assemble_nexo_graph 先保存固定候选及来源，Step11 按该候选版本审核；通过后 deliver_nexo_graph 交付相同内容。候选组装不要求先有审核报告，候选变更后必须重新审核；两个内部动作均不增加用户确认步骤。

### 2.5 验收要求

| 场景 | 预期行为 |
| --- | --- |
| 章节阶段追问早期决策 | 跨 Session 搜索并读取原始出处 |
| 最新版本为草稿、旧版有效 | 默认读有效版本；显式读草稿时保留真实状态 |
| 部分内容确认 | 返回准确确认范围 |
| 请求范围无有效版本 | 返回 `no_effective_version`，不回退草稿 |
| 命中已替代方案或旧摘要 | 返回真实状态、版本及可读原始依据 |
| 分页期间产物更新 | 保持原版本和准确读取范围 |
| 搜索无匹配或存储故障 | 分别返回 `no_matches`、`read_error` |
| 引用其他项目 ID | 不返回跨项目内容 |
| 执行只读工具 | 不改变产物、确认或流程状态 |

## 3. 可调配置与 HTML 配置入口

### 3.1 配置范围与继承

统一配置管理 instructions、全部模型输出结构、最终 Graph 契约、上下文材料、历史窗口、检索、压缩、模型参数和工具权限。HTML 配置入口集成在第 9 节的对话页面中，与运行时读取同一配置源。下列键为 Harness 配置键，由适配层映射到 Agents SDK 和内部服务；不支持的参数或组合必须在发布前报错。

继承顺序：全局默认 → 项目覆盖 → 项目内 Agent 配置 → 阶段／辅助任务覆盖。未填写字段继承上层；列表整体替换。恢复继承与显式空值分别处理，预览显示最终值、来源和版本。

| 工具 | `tools.enabled`、`tools.descriptions` | 业务 Agent 按需启用 `get_artifact`、`search_records`、`read_record`；纯摘要任务使用已准备材料 | 工具开关与业务描述；工具 Schema 和执行逻辑由代码管理 |

所有 Agent、阶段及辅助任务默认继承 `model.name=gpt-5.6-sol` 和 `model.reasoning_effort=medium`，可在同页配置区按作用范围覆盖。模型与推理设置保存为配置版本，按 3.4 在后续新运行生效。

有效输入预算 `B = min(解析后的阶段 context.input_token_cap, 模型上下文窗口 − model.max_output_tokens − context.safety_margin_tokens)`。输出预留与本次输出上限一致，包含推理与可见输出；适配层校验模型窗口、输出及推理 token 约束，配置必须留有有效输入空间。Step1 默认 `B=256000`，原文上限 200000 仍须与其他实际输入合并检查，不预先保证剩余空间一定足够。

模型能力由适配层按受支持模型维护。当前默认模型 `gpt-5.6-sol` 的官方上下文窗口为 1050000、最大输出为 128000 tokens，参见[模型文档](https://developers.openai.com/api/docs/models/gpt-5.6-sol)。这些能力值与项目／阶段配置上限分别展示；更换模型后重新校验，不把提高项目上限当成扩大模型窗口。

历史预算、摘要长度和检索数量不能导致未完成工具交互被截断或必需信息被丢弃。Step1 按全文准入规则拒绝超限调用；其他阶段超预算按 1.6.5 处理，并记录适用的分批覆盖范围。全剧审核、长章节生成等任务使用各自的配置覆盖。

### 3.3 Instructions 与输出结构编辑

最终 instructions 由共通模板、Agent 职责模板和当前阶段／辅助任务模板组合，保留各部分的来源与版本。模板只能引用已声明的运行时变量；必填变量缺失时校验失败。原作、历史对话、产物正文和检索结果作为上下文数据加载。

同页配置区必须支持编辑全部输出类型的字段、嵌套结构、类型、枚举、必填／可空、约束、中文说明及示例。输出字段以绑定的 `output_type`／业务 Schema 为准。发布结构变化时，同步校验提示词、下游读取、确认路径、业务校验器、迁移与导出映射；字段改名、删除和类型变化必须显示受影响的消费者。未实现的新语义或模型不支持的结构阻止发布，具体规则见 6.6。

### 3.4 保存、发布与生效

1. 编辑保存为配置草稿，记录版本、作用范围及父版本。
2. 发布前校验数值范围、模型能力、模板变量、工具可用性、Schema 支持、消费者与确认路径、导出映射、阶段必需来源。结构变化还需通过迁移和样例校验。
3. 运行启动时解析继承并固定配置快照；本次模型调用、材料读取、工具限制及摘要处理均使用该快照。新发布配置仅对后续新运行生效。
4. 暂停恢复默认沿用原配置；显式迁移须在继续执行边界重新校验输入和版本。Steer 不切换配置快照。
5. 运行及产物记录配置版本、提示词版本、Schema 版本与哈希、映射与校验器版本、材料引用。旧产物按原 Schema 读取，迁移生成新内容版本；已有确认不扩展到新增或语义变化的字段。

配置回退重新启用历史版本，只影响后续运行；原运行快照、产物、确认及原始记录保留。摘要策略变化在下一次需要摘要时生成新摘要版本。

用户明确继续触顶任务或调整其预算时，按 4.5 记录针对该任务的新限额／追加额度及生效检查点；不改写旧调用快照，也不顺带切换模型、提示词或 Schema。普通配置发布不自动恢复触顶任务。

项目隔离、原始归档、确认依据、固定版本引用、来源追踪和工具协议完整性不可关闭。配置发布不触发业务产物确认。最终 `nexo_graph` 仍须满足第 6 节的领域契约与业务校验，Harness 审计与确认信息单独保存。

### 3.5 同页配置区

配置区在对话页面内展开和收起，编辑配置时保留当前项目、会话和输入草稿。用户可直接使用已发布配置完成改编，配置编辑不是业务流程的必经步骤。配置发布与运行快照遵守 3.4。

| 页面区域 | 必须提供的功能 |
| --- | --- |
| 配置范围 | 选择项目、Agent、阶段、辅助任务；查看继承关系与生效版本 |
| 提示词 | 编辑模板、查看变量、预览组合后的 instructions |
| 输出类型 | 编辑全部字段树与 JSON Schema、说明和样例；预览对话内产物展示及阶段绑定 |
| 输出兼容性 | 查看消费者、确认路径和 Graph JSON 映射的影响；校验样例、配置迁移、显示发布阻塞原因 |
| 上下文 | 设置分阶段材料来源、自动／按需加载、字段与范围筛选、近期历史、预算及压缩参数；显示实际继承值与固定来源 |
| Step1 全文准入 | 在阶段配置中调整原文上限、总输入上限、输出上限／预留和安全余量，展示各项继承值与来源、所选模型窗口及输出能力、固定原作版本、全文 token 数、其他实际输入、`B` 与准入结果；`full_text`／`reject` 只读，超限不分批、截断或摘要降级 |
| 后续阶段分批处理 | 为适用阶段配置自然边界顺序、批次目标与上限、邻接和衔接预算、条目数；只读预览批次边界、token 估算和覆盖计划；不作用于 Step1 |
| 依赖与版本映射 | 编辑已注册字段映射与转换，查看被影响的消费者、可保留／需复核／需重新确认范围；预览不改变正式状态 |
| 模型与工具 | 选择模型和推理强度，显示继承后的实际值；默认 `gpt-5.6-sol`／`medium`；设置其他受支持的模型参数、调用上限、工具及读取限制 |
| 重试与预算 | 配置临时失败重试次数、输出修复轮数、任务耗时和费用限额；展示累计消耗与剩余额度 |
| 组装预览 | 只读组装指定任务材料，展示内容、版本、来源、选择理由、token 估算、省略原因及重新读取方式 |
| 版本管理 | 保存草稿、校验、查看差异、发布、恢复继承及回退 |

组装预览区分完整材料与片段、已确认内容与待处理修改，并显示缺失来源、过期依赖及超预算原因。预览不触发生成或确认；正式运行前重新校验实际输入。

## 4. 运行中消息处理与版本一致性

本节规定业务语义；完整状态、事件、队列、恢复和并发裁决以独立维护的[运行状态机与调度契约](runtime/运行状态机.md)为准。检查点恢复载荷绑定 [checkpoint-state.schema.json](runtime/checkpoint-state.schema.json)。

### 4.1 运行控制语义

Task 是业务任务，可跨多次 Run、等待和恢复。Run 是受控执行段：runner 段至多调用一次 Runner，可含多轮模型与工具；recovery 段只核对及处理已保存结果，不调用模型。任务生命周期独立于浏览器连接和平台登录会话。Run 已成功返回不代表产物已经确认或整个 Task 已完成。

| 方式 | 处理规则 |
| --- | --- |
| Steer：调整当前任务 | 保存新要求，在后续执行边界纳入当前任务，保留目标、历史及已完成进度；明确改变目标时按业务变更处理 |
| Queue：排队处理 | 持久保存后续请求，当前任务继续；轮到请求时启动新运行，按任务范围选择 Session |
| Interrupt：停止当前任务 | 请求中止指定运行，停止调度该运行的新模型调用与工具操作，记录实际停止状态 |

运行中的新消息在提交时由用户明确选择 Steer 或 Queue，将所选方式与原始消息一起持久保存；不由 Agent 代选。该选择是每条请求的运行控制信息，不继承项目默认配置。停止为独立操作；用户明确要求立即停止时执行 Interrupt。

运行控制方式与业务确认独立判断，确认遵守 1.5 的明确表态规则。补充要求只作用于明确范围，询问影响不触发修改。排队确认在轮到处理时才生效，绑定提交时明确指向的版本，不按出队时最新稿重新解释。缺依赖的排队生产请求可先记 blocked，允许后续确认解除等待，具体调度见独立契约第 4 节。

### 4.2 消息接收、纳入、停止与恢复

| 执行环节 | 约束 |
| --- | --- |
| 接收 | 先保存原始内容、消息 ID、项目与任务范围、处理方式、目标运行，再处理；记录待处理、已纳入、已取消等实际状态 |
| Steer 纳入 | 在后续模型调用前的可用执行边界纳入，记录实际采用消息的调用；已开始的模型请求和工具操作保持原输入 |
| Session 写入 | 经运行控制层串行写入；不启动另一运行并发修改同一 Session |
| 结束竞争 | 消息到达与任务结束交错时重新核对目标状态，保留消息并返回真实状态，不丢失或误投其他运行 |
| Queue 启动 | 重新解析配置、有效决策和依赖版本；保留用户显式指定历史版本的意图；排队请求此前不进入当前生产输入 |
| Interrupt | 分别记录“停止请求已收到”和“运行已停止”；保留已完成写入；记录并核实仍在执行或结果未明的操作 |
| 恢复 | 核对已完成写入、未完成操作、当前依赖和配置快照后继续，避免重复执行或覆盖已完成工作 |

Interrupt 不回滚既有产物和历史。等待确认或澄清时，Harness 保存等待状态与继续位置，结束当前模型请求；恢复时按检查点重新组装输入。

#### 4.2.1 离开页面与重新登录

关闭页面、浏览器断开连接或退出登录不会取消已启动的任务。服务端按已授权范围继续执行，直到任务完成、等待用户决定、收到主动停止请求或遇到需要处理的异常。再次登录只读取服务端最新状态、结果和待处理事项，不因重连重复启动任务。

等待确认或补充信息时保存等待状态并释放执行资源；用户离线不构成确认。主动停止必须记录停止意图，再按 Interrupt 规则处理正在执行的操作。

#### 4.2.2 服务端重启与异常恢复

服务恢复后，按持久化状态检查未完成任务：

| 已保存状态 | 恢复动作 |
| --- | --- |
| 正在执行，且可定位有效检查点 | 核实原执行实例状态、已完成写入与结果未明的操作；确认无重复执行者且未触及任务上限后，从最近有效检查点自动继续 |
| 等待用户确认或补充信息 | 保持等待，不自动开始模型调用 |
| 已收到主动停止请求或已停止 | 完成必要的停止处理并保持停止，不自动重启 |
| 已完成 | 展示保存的结果，不重新执行 |
| 无法确定恢复位置，或达到重试／修复／运行预算上限 | 保持暂停并保存原因及已完成进度，不因服务恢复自动重试 |

恢复前读取持久化的暂停原因、轮次、重试／修复计数及任务用量，服务重启不清零；只有被服务故障打断且仍可执行的任务自动继续。恢复继续使用固定配置快照，并重新检查输入和依赖版本；上游变化按 4.3 处理。恢复不得重复提交已完成的写入，也不得将未核实的操作当作成功。检查点描述可继续执行的应用状态，不依赖原进程或未完成模型请求仍然存在。

默认每 Task 最多自动恢复 3 次；超过上限保持暂停。故障续跑继承原模型轮次余额，例如额度 10、已用 7，只能再用 3；零余额仍可处理已保存结果，但不能再调用模型。普通完成、等待用户、暂停与停止后的旧 Run 不重新激活，后续执行建立新 Run 并保存恢复关系。

### 4.3 业务变更与结果生效

上游产物或玩家身份、原作保留范围、禁止结局等决定改变时，Harness 登记变更及原始消息出处，检查活动任务和下游产物对被修改内容的实际依赖。

| 影响判定 | 处理方式 |
| --- | --- |
| 不影响本任务依赖 | 继续当前任务，已有产物保持有效，保存判定依据 |
| 影响明确且修改方式确定 | 暂停受影响旧任务的后续生成与结果生效；更新输入后，在已授权范围内自动生成局部修复草稿 |
| 影响明确但需要新的创作取舍 | 标明受影响内容与可选方案，等待用户决定后修复 |
| 影响范围不明 | 标记相关任务／产物需复核，先完成影响检查；不推进依赖它们的步骤，不阻塞无关任务 |
| 变更后旧任务返回结果 | 可按原依赖版本保存为需复核草稿；不能覆盖有效结果或标记为满足新要求 |

新版本和修复草稿保留原版本及确认记录，不直接覆盖有效结果。修复沿用阶段确认规则，仅对变化范围核实确认；未改内容在来源、语义和依赖仍有效时保留确认依据。只有内容或依赖的实际变化才触发复核，不因版本号变化全部重跑。

依赖检查在后续模型调用、相关写入和结果生效前执行。保存／生效必须防止检查与写入之间的版本竞争；迟到结果遵守同一规则。

业务依赖切换在明确的继续执行边界重新组装输入并保存新版本清单，此前调用保留原依赖引用。重大上游变化按 1.4 更换 Session。业务输入更新与配置快照分别管理，不能通过追加消息改写历史调用的依据。

### 4.4 调用失败与输出修复

| 情况 | 处理方式 |
| --- | --- |
| 网络中断、超时、临时限流 | 延迟后重试同一操作，默认最多重试 2 次，含首次最多尝试 3 次 |
| 模型输出格式错误，或修改方式明确的业务校验问题 | 返回具体错误与相关草稿，由对应 Agent 修复；同一产物生成／修改任务默认最多自动修复 2 轮 |
| 缺少必要信息或需要新的创作取舍 | 保存等待状态，暂停依赖该信息的任务并询问用户 |
| 密钥、权限、Schema 配置等错误 | 停止重复调用，记录需要修正的配置或权限问题 |

临时失败重试按同一操作累计，SDK 内部重试与 Harness 重试共用上限，不能叠加成多组 3 次尝试。输出修复针对已生成结果重新调用模型，与原调用失败的重试分别计数；修复产生新的明确问题仍消耗同一任务的修复额度。

达到上限仍未成功时，保存已完成进度、可用草稿、错误及尝试记录，进入待处理状态。已完成写入不得重复提交；结果未明的操作先核对执行记录。修复不绕过确认规则，也不自行改变已确认的关键设计。

所有重试、修复及子任务消耗计入所属任务预算；每次重试或修复开始前均检查 4.5 的限额。

### 4.5 运行上限、暂停与继续

当前测试版本关闭费用门禁：预算超额和已知终态调用的费用未知均不阻塞任务、续跑或队列。费用与 token 统计继续保存；未知费用保持未知，不补零。页面不要求费用追加、未知费用确认或费用补录，旧 `task.max_cost` 配置暂不生效。开关为 `branch_agent/engine.py` 中的 `COST_GATES_ENABLED=False`，对已有冻结任务同样有效；费用门禁代码保留以便后续恢复。

| 限制 | 计数范围与触发行为 |
| --- | --- |
| 模型轮次 | 每次 `Runner.run()` 默认 `max_turns=10`，统计 SDK 执行循环中的模型轮次；不按用户消息数或失败重试次数计算。触及轮次限制时由 Harness 保存已有检查点并转为暂停 |
| 任务执行耗时 | 按阶段／章节任务累计实际执行时段，包含自动重试和修复；等待用户确认、澄清或排队的时间不计入 |
| 任务费用 | 累计所属调用、重试、修复及子任务的计费用量，按所选模型及计量配置核算；同一调用不得在父子任务中重复记账 |

新调用前检查启用的剩余额度；响应返回后更新用量及检查点。并行子任务共享父任务限额，服务重启、换执行实例或新建运行不清零累计消耗。任务耗时限额通过同页 HTML 配置区管理；测试版隐藏费用限额表单，费用计量与所选模型对应。

触及启用的运行上限后：

1. 停止为该任务发起新的调用，保存已完成进度、可用草稿、暂停原因、累计用量及恢复位置。
2. 核实已经发出或结果未明的操作；迟到结果关联原任务记录，不因此自动恢复执行。
3. 向用户展示触及的限制和已完成范围，等待明确选择继续或调整预算。普通消息、重新登录、服务恢复或配置发布不解除该暂停。
4. 继续前确定新的限额或追加额度，记录用户依据及生效检查点，重新核对配置、输入版本和未完成操作后恢复。累计历史消耗保留；不得通过自动新建 `Runner.run()` 绕过上限。

配置覆盖与业务确认分别管理。恢复可继续生成草稿，但已确认设计、产物生效及最终交付仍遵守第 7 节。

## 5. Agent 定义与协作

### 5.1 架构与共通配置

系统定义 1 个对话协调 Agent 和 6 类专业 Agent。Python 调度层负责流程状态、依赖检查、确认落库、版本管理和运行控制，直接调用主线专业 Agent。不同章节复用同一 Agent 定义，分别传入任务范围、材料和 Session。

共通要求写入 `prompts.base`，角色要求写入 `prompts.agent`，步骤要求写入 `prompts.stage`。同一 Agent 覆盖多个步骤时，每次仅绑定当前任务的提示词、材料配置及输出 Schema。

| 共通要求 | 规则 |
| --- | --- |
| 输入与来源 | 按 1.6 固定材料版本；区分原作事实、改编设定、已确认决定、草稿与推测；原始材料和历史记录作为数据读取 |
| 输出与保存 | 按第 6 节绑定的 Schema 输出；阶段信封携带来源和依赖，直接 `nexo_graph` 的来源存入 Harness 外壳；身份、修订、时间、版本、保存与生效由程序管理 |
| 模型与预算 | 遵守第 3 节的继承、预算、压缩和调用限制，运行内固定配置快照 |
| 工具权限 | 使用第 2 节只读工具；保存、确认和运行控制由 Harness 执行；新增工具须补齐接口契约和角色配置 |
| 完成与生效 | 合格草稿表示本次生成完成；阶段推进另需满足确认、依赖与校验条件；审核完成可以返回不通过结论 |
| 暂停与故障 | 返回原因、缺项和继续位置，由 Harness 保存等待状态；中断、调用失败、预算耗尽记录为对应运行状态 |
| 消息关联 | 转交要求保留原消息 ID、内容和范围；多个 Session 引用同一原始归档，转述不能作为新的确认依据 |

### 5.2 默认流程与跳转

默认按 Step1～Step11 推进；在依赖有效的前提下，支持跳过已有产物的生成步骤、直接进入后续阶段、返回修改和局部重做。程序在已授权任务范围内自动推进到下一决策点。阶段确认、章节循环及交付规则见第 7 节。

### 5.3 对话协调 Agent

| 配置项 | 定义 |
| --- | --- |
| 标识 | `conversation_coordinator` |
| 职责 | 理解用户请求、澄清范围、解释产物与进度、回答历史问题，提出任务及修改请求；专业生产与流程状态由对应 Agent 和程序处理 |
| 阶段 | 全阶段用户交互入口 |
| 输入 | 当前消息及 ID、项目概况、阶段／章节状态、活动任务与队列摘要、决策和产物索引、近期交互；按需加入专业结果片段、待确认项与历史证据 |
| 输出 | 用户回复／澄清问题；独立的任务请求，含操作意图、目标阶段／章节／产物、版本意图、原消息引用；涉及确认时提出候选对象和范围供程序核实 |
| instructions | 识别讨论、查询、生成、修改或确认意图，保留用户指定范围及跳转要求。根据真实运行状态说明进度；历史回答引用原始证据，缺失时明确说明。仅对影响执行的关键信息追问，不代替用户确认，不将建议或任务请求表述为已执行结果。 |
| 工具 | `get_artifact` 核对结果、版本和确认范围；`search_records`、`read_record` 查历史证据；主线任务请求交调度层 |
| Session | 项目级协调 Session；保存近期交互、项目概况和未完成事项；专业产物按引用／片段加载 |
| 完成条件 | 问题已据实回答，或任务请求已由程序处理并说明真实状态；待澄清时返回具体问题。回复完成与专业任务完成分别记录 |

### 5.10 调用与协作协议

| 场景 | 调用方式 |
| --- | --- |
| 主线生产 | Python 调度层检查依赖与确认后直接调用专业 Agent，管理步骤状态与产物生效 |
| 对话与跨阶段查询 | 协调 Agent 回答或返回任务请求；专业产物可直接展示，解释时按需读取 |
| 局部辅助任务 | 可用 Agent as Tool，限定输入、范围、来源、预算和输出，完成后返回调用方，不推进主线 |
| handoff | 默认不启用；若增加专家接管，须先定义接管范围、历史过滤与恢复规则 |
| 审核修复 | 程序按问题归属派回策划、结构、设计或生成 Agent；保存新草稿，检查确认与下游影响后复核指定版本 |

专业任务说明必须包含项目、目标阶段、章节／分支范围、原消息引用、输入版本、预期产物、约束和 Session。Agent 返回草稿、来源及覆盖情况，或明确缺项／问题；Harness 校验并记录实际状态。

局部子任务使用独立工作历史，返回必要结果、简要依据、引用和依赖版本，完整记录进入原始归档。父任务只提供所需材料；子任务日志不全量追加到协调 Session。

UTF-16 换算、读取范围记录、版本分配和确认记录由程序负责；首版产物质量程序校验限定为 8.2 的两项。确定性检查失败时，程序将具体问题交适当 Agent 修正；模型的“通过”或“已确认”声明不能单独改变业务状态。

## 6. 输出类型与数据契约

### 6.1 最终输出：`nexo_graph`

最终 `output_type` 为 `nexo_graph`，返回一个 `Project` JSON，供剧情树和剧本视图共用。

- 完整定义：[nexo_graph.schema.json](/Users/llj/HKU/Agent_Harness_Develop/docs/output-schemas/v2/nexo_graph.schema.json)
- 数据示例：[nexo_graph.example.json](/Users/llj/HKU/Agent_Harness_Develop/docs/output-schemas/v2/examples/nexo_graph.example.json)

| Project 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 项目 ID |
| `name` | string | 作品名称 |
| `description` | string | 作品简介 |
| `prompt` | string | 项目提示词 |
| `revision` | integer | 项目修订号 |
| `updatedAt` | string | 更新时间 |
| `chapters` | Chapter[] | 按阅读顺序排列的章节 |
| `chapterEdges` | ChapterEdge[] | 章节连线 |
| `variables` | Variable[] | 全局变量定义及初始值 |
| `scenes` | Scene[] | 项目共享场次 |

`Chapter` 包含 `id / title / summary / nodes / edges`。`nodes` 保存该章节点，`edges` 保存章内连线；正文展示按数组顺序，剧情走向按连线。

`StoryNode.kind` 支持五种类型：

| kind | 用途 | 主要业务字段 |
| --- | --- | --- |
| `story` | 剧情正文及互动 | `body`、`synopsis`、`sceneId`、`choiceGroups`、`qtes` |
| `variable` | 修改全局变量 | `scriptDsl` |
| `condition` | 按条件分流 | `branches[].conditionDsl` |
| `game` | 进入小游戏 | `gameUrl` |
| `jump` | 跳转到节点或章节 | `jumpTarget` |

节点同时保存 `id/title`、布局 `x/y/collapsed` 和边界标记 `chapterStart/chapterEnd`。非适用字段按 Schema 填写空字符串、空数组或 `false`。`body` 保存完整正文；选项／QTE 在正文中的位置由 `scriptInline={version:1,afterLine,order}` 指定，`afterLine` 从 0 开始，同一行的互动按 `order` 排序。

默认按章生成 `chapter_graph`，由程序汇总成最终 `nexo_graph`；整剧生成任务直接绑定 `nexo_graph`。最终 JSON 根对象就是 `Project`，来源、确认和运行记录单独保存。

### 6.3 阶段返回格式

除 `nexo_graph` 和 Step2 的两份纯文本产物外，其余结构化类型使用统一返回结构：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `result_kind` | `ready / needs_input` | 完成业务内容或等待补充信息 |
| `payload` | 对应业务对象或 null | `ready` 时必须完整；缺少信息时可附未完成草稿 |
| `questions` | Question[] | 问题 ID、内容、原因、目标字段、候选答案和阻塞范围 |
| `evidence_refs` | EvidenceRef[] | 实际使用的记录、版本及位置 |
| `notes` | string[] | 补充说明 |

`ready` 不得包含未解决的阻塞问题；`needs_input` 必须列出具体缺项，所附草稿仍须满足 Schema，否则 `payload=null`。产物确认与生效由 Harness 按用户记录处理。整剧模式在必需材料齐备后执行，失败或阻塞写入运行记录，不往 `Project` 增加返回状态字段。

业务引用统一使用 `EvidenceRef={record_id,version,item_id,json_pointer}`。版本化记录必须指向具体版本；当前产物内部的新对象通过局部 ID 引用，保存时统一解析为稳定 ID。确认范围关联对象版本及稳定条目 ID，字段路径不能替代对象身份。

原作 `SourceAnchor` 使用固定文本版本的 UTF-16 半开区间。引用程序提供的可信索引时，`exact_quote` 可为 null，但区间两端必须是合法整数；不要求为声明全本覆盖重复输出完整原文。索引不可信时提供原样短摘录，由程序唯一定位；有多个匹配时报告歧义。Graph 的 `scriptInline.afterLine` 则使用节点正文行号，单独计算。

### 6.4 阶段业务规则

| 类型 | 必须满足的规则 |
| --- | --- |
| `source_views` | 根据同次输入中的完整原文生成全局事件与人物双视图；两类事件 ID 独立，每个事件各自直接锚定原文，完成时覆盖全本且 remaining_source_anchors 为空；未完成范围仅用于缺项定位，不代表批次进度 |
| `source_global_analysis` / `source_character_analysis` | 分别表达全局事件与主要人物分析；两份产物独立保存、确认和引用，用户实际选择另存为决策 |
| `adaptation_plan` | Step4 初稿的后续阶段引用可为 null；后续确认结果写入新的方案版本，已生成产物仍保留其原输入版本 |
| `game_event_view` | Step5 游戏事件是独立于 Step1 两种事件的新设计，直接锚定固定原作；非纯新增事件必须有区间。Step6 必须复用 Step5 的全部事件 ID、事件关系和原文索引，只补充 `events[].narrative_function`；事件的时间、因果和备选关系在章节设计时转为具体路线 |
| `ending_routes` | 明确候选结局、大致路线及进入条件；路线只引用输入事件视图中存在的业务事件 ID，来源版本由 Harness 记录 |
| `player_profiles` | 画像关联设计依据；无调研证据的判断列入 assumptions |
| `chapter_design` | `game_event_refs` 指定本章由哪些 Step5/6 游戏事件组成；Harness 将这些事件的已验证原文锚点合并写入 `chapter_source_anchors`，模型不填写章节边界。`linear_body.segments[]` 保存完整正文且只保留一份正文来源；互动以段 ID 定位；所有走向统一写在 `flow_links`；效果与条件必须有可实现的节点映射 |
| `chapter_graph` | 返回完整章节，保留未修改内容；共享场次／变量作为提案统一核验；移除节点／边须列明 ID |
| `review_report` | 固定被审版本，记录已查／未查范围；问题用稳定对象 ID 和字段路径定位，结论基于实际检查证据 |
| `work_summary` / `subtask_result` | 保留来源和限制；摘要不新增确认，子任务结果返回父任务且不直接推进主线；所有实际输出均归档 |

`graph_compatibility` 使用 `compatible / requires_lowering / blocked / unresolved`，记录转化方法和具体冲突。正式生成前必须解决影响执行的缺项；需要改变已确认设计时按变更流程处理。

Step9 的选项使用 `options`，QTE／操作类互动使用 `outcomes`；同一结果只有一处权威走向。`continue` 必须映射到当前节点正文内的后续内容；跨节点或跨章的承接显式建模。

可选校验 Agent 固定读取一个 Project 版本，`findings[].graph_targets` 定位具体对象。脚本检查由 Harness 独立保存，不作为 Agent 输入，报告中的 `graph_checks` 固定为空数组。

### 6.5 Graph 生成、合并与校验

`chapter_graph.payload` 的结构：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `chapter` | Chapter | 目标章节的完整快照 |
| `shared_scenes` | Scene[] | 共享场次的新建／变更提案 |
| `shared_variables` | Variable[] | 全局变量的新建／变更提案 |
| `removed_node_ids` | string[] | 相对输入版本移除的节点 |
| `removed_edge_ids` | string[] | 相对输入版本移除的连线 |

生成和合并规则：

1. 固定项目、章节及共享材料版本。长章可先拆为子任务，交付 `ready` 前汇总成完整章节。
2. 已有 ID、节点类型、布局和项目元数据保持稳定；新增 ID 由程序分配或解析，布局由程序初始化。项目修订号与更新时间由程序维护，项目提示词仅按授权修改。
3. 基线中消失的节点／边必须与 `removed_*` 精确一致，并核验修改范围与引用清理。节点内部对象的移除同样检查差异与授权。整剧模式在 Harness 记录完整增改删差异，省略不自动构成删除许可。
4. 仅合并获准修改的章节与字段，保留其他章节及原工程中未涉及的制作数据。共享对象按 ID／变量 key 协调，冲突显式处理；不按返回先后覆盖。
5. 组装后按 `nexo_graph` 字段契约提取并校验交付 JSON，保存新草稿及依赖版本，再按 7.2、7.4 的阶段确认与交付规则生效；已审核内容的最终组装不增加人工确认。更新原工程时，保留额外字段的完整对象按完整编辑器领域模型校验。

Graph 创作与数据规则如下；首版自动检查仅执行 8.2 的两项，其余规则作为生成约束和审核 Agent 的审读依据，后续逐步扩展算法：

| 对象 | 校验要求 |
| --- | --- |
| 身份与引用 | ID 唯一、目标存在、归属正确；完整交付时无未解析跨章或共享实体引用 |
| 正文与顺序 | story.body 是完整正文；章节／节点数组决定阅读顺序，编号只统计 story；检查已确认设计及分支内容覆盖 |
| 场次 | 项目全局共享；只有 story 可关联，未关联时 sceneId=''；人物／地点 ID 由实体目录解析，显示名称与引用一致 |
| 变量 | `type=number/string/boolean`，value 始终是字符串；数值必须有限可解析，布尔仅 true/false。DSL 引用已定义 key，并遵守目标语法和类型；operations=[]，条件分支的 mode='and'/conditions=[]，实际逻辑写入 DSL |
| 章内连线 | source/target 同章，sourcePort 有效且至多一条边；禁止直接自连或连接章开始。普通出口 next，条件 branch.id/default，选项 choice.id，QTE qte.id 或 qte.id:failure |
| 互动 | afterLine 在正文范围内；jump 目标与可视边一致；continue 目标为空且无可视边。QTE 禁用失败时无失败边，可保留合法草稿目标；选项无失败／超时出口 |
| 节点出口 | 含 choiceGroups/qtes 的 story 关闭 next；jump 无普通出边。条件／状态效果使用 condition/variable 节点；条件按 branches 数组顺序首命中，default 为独立兜底；小游戏使用 next 出口和可信 gameUrl |
| 章节边界 | 完整章节有且只有一个开始节点；开始／结束互斥，仅 story/game 可设置；章结束的出边只能连接同章 jump |
| 章节关系 | 程序按章节顺序生成 begin→首章→…→末章→end；跨章仅直接下一章。jump 的 node 目标为同章或下一章的非开始 story 节点，chapter 目标为下一章入口 |
| 路线与结局 | 检查路径可达、条件可满足和结局覆盖；循环不自动恢复变量，超出目标能力的设计返回冲突处理 |

首版交付为第 9 节规定的 Nexo Graph JSON 文件，页面提供查看、复制和下载。

### 6.6 output_type 配置

全部输出类型使用第 3 节统一的 HTML 配置入口，支持字段、嵌套结构、类型、枚举、约束、说明、示例和任务绑定。

Schema 按完整版本绑定，不对字段做隐式深度合并；严格输出编译保留消费者要求的必需字段和类型，不自动改为可空。字段映射只使用已注册转换，HTML 配置不执行任意代码。

修改 Schema 时同步检查 instructions、下游字段读取、确认路径、业务校验和组装映射；业务规则的放宽须显式配置并完成适配。`chapter_graph` 与 `nexo_graph` 的共享领域定义必须保持一致。发布后生成新的不可变版本；旧运行沿用固定快照，迁移生成新产物并复核确认范围。

### 6.7 Agents SDK 接入

- 以注册表选择 Schema，通过 `AgentOutputSchemaBase` 适配为 `Agent.output_type`；Schema 提供及 JSON 解析校验使用同一版本。
- 也可从同一 Schema 生成 Pydantic 类型，不维护独立的手写定义。
- 调用前校验模型支持的严格输出结构；结构配置错误暂停并修正配置，模型格式错误及可确定修正的业务错误按 4.4 反馈对应 Agent 修复，缺少信息走 `needs_input` 或协调流程。
- 运行和产物记录 Schema 版本／哈希、instructions、映射及校验器版本。两项程序检查按 8.2 执行；可选校验 Agent 的判断不会被记为脚本检查结果。

### 6.8 输出验收要求

- 所有任务绑定可解析到确定的 Schema 版本，返回字段、类型和引用符合定义。
- 单章生成与整剧生成都产出同一 Project 结构，正文及设计范围完整。
- 最终输出通过 Schema 与不可达节点检查；配置了校验 Agent 时还须按第 8 节通过。
- 用户确认、生效状态、依赖版本和来源保存完整，模型返回状态不能替代这些记录。
- 修改任一 output_type 后能预览结果和下游影响，错误配置在发布或调用前被阻止。

## 7. 流程编排与人工确认

### 7.1 调度与自动推进

协调 Agent 识别用户意图和任务范围，Python 调度层检查输入版本、依赖、确认及校验结果后执行。默认按阶段顺序推进，阶段编号不要求每一步都重新生成。

| 用户请求 | 调度规则 |
| --- | --- |
| 完成整部改编 | 在授权范围内自动执行到下一决策点；用户确认后继续，全部章节完成后进入全剧审核 |
| 完成指定阶段或章节 | 完成该范围后停止，不自动扩大到其他章节或整部改编 |
| 跳过生成步骤 | 复用已有有效产物或用户提供的替代材料，检查字段、来源、依赖和必要确认；缺少时列明缺项 |
| 直接进入后续阶段 | 检查目标阶段所需材料；齐全即执行，缺失时补齐后继续 |
| 返回修改 | 定位指定版本，按 4.3 检查影响并保存新草稿，保留后续历史与未受影响产物 |
| 提问、讨论或查看历史 | 回答问题，保持生产进度、产物与确认状态 |

格式校验、保存、上下文组装等程序操作自动执行。缺少关键输入、存在冲突或需要新的创作决定时保存等待状态；仅暂停依赖该缺项的任务。停止指令进入第 4 节运行控制流程。

用户提供的替代产物登记为用户来源的版本化材料，保留导入和确认依据。用户授权继续执行不等于提前确认尚未生成的内容。

### 7.2 阶段确认与生效

确认按 1.5.2 执行：明确表态即确认，含糊时询问；确认关联实际展示的版本与范围。一次可以确认多个明确指向的条目，部分确认只供依赖该范围的任务使用。

| 阶段 | 推进条件 |
| --- | --- |
| Step1 | 切片覆盖、双视图与来源引用检查通过后自动继续；程序校验不登记为用户确认，有阻塞歧义时询问 |
| Step2 | 两份分析均生成并分别确认；本阶段不要求用户额外回答创作偏好 |
| Step3 | 用户明确玩家身份与互动想法；明确采用默认策略后不重复询问默认策略 |
| Step4 | 改编方案通过检查并独立获得用户确认后，成为 Step5 确认结果的程序写回目标；不进入 Step5 模型输入 |
| Step5～Step8 | 游戏事件、叙事功能／玩家意图、结局路线、玩家画像分别确认后供下游使用 |
| Step9 | 用户确认当前章节的完整线性正文与互动设计版本，供同章 Step10 使用 |
| Step10 | 章节正文与 Graph 通过校验，用户确认后按任务范围进入下一章或全剧审核 |
| Step11 | 自动审核；通过且满足交付条件后自动交付，不增加整剧确认节点 |

Step5～Step8 的已确认结果写回方案并生成新版本，无须因汇总写回重复确认整份 Step4。改变已有关键决定时，仅针对实际变更核实确认并检查下游影响，不使未受影响内容自动失效。

### 7.3 章节循环

默认顺序为：第 1 章 Step9 → 确认 → 第 1 章 Step10 → 确认 → 第 2 章 Step9 → …… → 全剧审核。执行不得超出用户指定的章节范围。

开始逐章创作前，明确全剧路线、章节范围、共享变量和跨章约束。同章 Step9 与 Step10 使用独立 Session，以已确认 `chapter_design` 的固定版本衔接；跨章通过版本化产物和共享约束衔接。

用户可要求先完成全部章节设计，再统一生成。两种顺序均要求每章 Step10 开始前已有有效且满足确认范围的 Step9 设计；调整调度顺序不清空已完成结果或确认。

### 7.4 审核、修复与最终交付

全部章节完成并满足确认要求后，在整剧任务范围内自动进入 Step11。审核固定产物版本和检查范围；报告生成完成可以对应不通过结论。

发现 blocker 或 major 问题时按 4.3 交给对应 Agent 修复：修改方法明确且位于授权范围内时自动生成修复草稿；需要新的创作取舍时询问用户。minor 和 suggestion 保留在报告中，不阻断交付或强制启动返修。修复内容按对应阶段规则确认，再复核新版本及受影响范围。达到自动修复次数上限仍未解决时暂停，保留结果并说明具体问题；默认最多自动修复 2 轮，可通过 `repair.max_rounds` 配置，计数与预算遵守 4.4、4.5。

最终交付须同时满足：

1. 当前各章版本满足确认要求，依赖有效，无阻塞本次交付的待复核项。
2. 正文和分支范围完整。
3. 8.2 的两项脚本校验通过。
4. `prompts.validation` 非空时，可选校验 Agent 按 8.1 通过且没有未解决的 blocker 或 major；为空时跳过该模型调用。
5. 校验针对实际交付版本；期间发生修改时重新校验。

满足条件后自动交付最终 `nexo_graph`，不再要求用户额外确认校验报告或整剧结果。最终交付使用完成校验的固定候选，不再次改写创作内容。

## 8. 质量审核

### 8.1 可选校验 Agent instructions

`validation_agent` 由 `prompts.validation` 控制，默认值为空。空值表示关闭；填写并发布后，只对后续新运行启用。一次运行固定 instructions 及最终 `nexo_graph` 版本，Agent 输入中没有其他阶段材料、历史或脚本校验结果。`criteria_ref`、被校验版本和来源引用由 Harness 绑定。

具体检查重点完全由已发布 instructions 决定。默认不设置数值评分，`review_report.payload.metrics=[]`；`graph_checks=[]`，因为脚本检查由 Harness 单独执行和保存。

| 问题级别 | 含义与处理 |
| --- | --- |
| blocker | 违反校验 instructions 中的明确硬性标准，导致无法交付的问题；必须解决 |
| major | 有证据的严重剧情矛盾、人物所知或动机冲突、选择与后果明显不一致等；必须解决 |
| minor | 不影响主要理解和路线成立的局部表述或一致性问题；报告并可建议修正，不阻断交付 |
| suggestion | 创作偏好和可选优化；说明建议，不作为强制修复项 |

`proposed_verdict` 使用现有枚举：完整覆盖最终 Graph 且无 blocker／major 时为 `pass`；有确定的必改问题时为 `needs_revision`；最终 Graph 本身不足以形成结论时为 `inconclusive`。已有发现照常保留，不用猜测填补缺项。

报告完成可返回 `result_kind=ready` 和不通过结论。Harness 核对版本、覆盖范围、脚本校验与必要确认后决定是否交付；通过后不增加人工确认。

### 8.2 首版程序校验

首版产物质量程序检查仅包含以下两项：

| check_id | 执行位置 | 算法与失败条件 |
| --- | --- | --- |
| `schema_contract` | Step10 完整章节合并后；最终 Project 组装后 | 将 JSON 按当前绑定的 JSON Schema 校验；无法解析、缺必需字段、类型／枚举错误或出现禁止字段时失败，返回具体 JSON Pointer |
| `unreachable_nodes` | Step10 完整章节合并后；最终 Project 组装后 | 从每章 `chapterStart` 沿连线和可判定的变量状态遍历；无入边、断裂连线、从入口无路径，或只位于可证明永远为假的条件后的节点均失败，返回章节、节点／边及原因 |

`unreachable_nodes` 对已支持的布尔、比较和基础算术表达式，以及简单赋值／增减脚本做保守静态执行。遇到无法安全解析的 DSL 时按“可能可达”处理，避免误报；因此它能证明一部分恒假条件，但不声称是完整的 DSL 求解器。

两项结果由 Harness 保存为固定检查记录，不由模型签发。可选校验 Agent 不接收这些结果，`review_report.payload.graph_checks=[]`。

检查失败按 4.4 返回具体问题，并在对话中显示 check_id、字段／对象位置和失败原因；最多自动修复 2 轮。两项检查不是 Agent 工具，由 Harness 调用。

### 8.3 首版范围

当前只建设可选校验 instructions 与上述两项产物质量脚本检查。完整 DSL 求解、播放器执行验证和整个 Harness 的系统评测暂不纳入范围。

## 9. 对话页面与 JSON 交付

### 9.1 页面结构

首版提供一个服务端支持的 Web 页面，将对话与第 3 节 HTML 配置入口集成在一起。用户在同一会话中完成原作提交、需求讨论、阶段结果查看、修改、确认和最终交付。

| 页面区域 | 功能 |
| --- | --- |
| 项目／会话列表 | 新建改编项目、打开历史会话，展示最近任务状态；数据随平台账号保存 |
| 主对话区 | 展示用户消息、Agent 回复、当前阶段进度、待处理卡片和阶段产物；需确认时直接提供按钮，需回答时提供选项或输入框；长正文与 JSON 可展开查看 |
| 对话输入区 | 输入需求、粘贴原文或提交原作文件；运行中提交消息时选择“调整当前任务（Steer）”或“排队处理（Queue）” |
| 运行控制区 | 展示运行、排队、等待用户、暂停和完成等实际状态；提供独立停止入口，暂停时展示原因与继续入口 |
| 可展开配置区 | 编辑 instructions、全部 output_type、上下文／Session 策略、模型、工具、重试和预算；功能遵守第 3 节 |
| 可展开运行与数据区 | 可视化所有 Harness 记录；查看结构化详情与 JSON、任务时间线、版本差异、依赖、确认来源、实际上下文和用量；规则见第 10 节 |

原作内容解析后保存为固定版本，展示全文 token 计量和 Step1 准入结果；超限保留提交记录并说明尚未开始切分，不自动截断或分批。解析失败或存在无法读取的内容时，在对话内说明并请求补充。平台认证、项目权限、服务端持久化与离线执行遵守 1.3、2.3 和 4.2。

### 9.2 对话交互

1. 用户通过对话提出整剧或局部改编任务，协调 Agent 识别需求、缺项和任务范围，Harness 按第 7 节调度。
2. 阶段产物在对话中提供可读内容、产物版本与当前状态。需确认时显示“确认此版本／提出修改”，修改意见就在卡片内填写；需补充信息时提供建议选项和自定义回答框。自然语言对话仍可使用，但不能作为完成必需选择的唯一入口。
3. 待确认卡片绑定固定任务、版本和范围，按钮由服务端直接执行，不调用协调模型猜测意图。一个回答只解决对应问题，其他问题继续保留。明确自然语言表态按 1.5.2、7.2 生效；查看、展开或下载产物不构成确认。
4. 查询历史、回到前面修改或跳转阶段均可在对话中提出，由既定依赖和确认规则处理。用户不需要选择内部 Agent 或工作 Session。
5. 页面按服务端执行事件更新进度，展示当前任务、已完成工作和等待原因；进行中的流式片段与正式产物分别标记，不能提前显示完成或通过。
6. 关闭页面后任务按 4.2 继续；重新打开会话恢复历史、产物、队列及待处理事项，不重复启动任务。

运行暂停卡片同时展示真实原因、受影响范围、旧运行配置与当前发布配置，以及可执行操作。普通继续保留旧配置；用新配置重做必须创建替代任务并保留历史。重新导入原作使上游产物失效时，提示从失效阶段重建，不能承诺直接复用旧产物。测试版缺少用量的已知失败调用只保留费用未知记录，不要求费用确认；远端结果仍未知时不能通过点击按钮假定失败或重复执行。排队请求逐项展示和处理，不通过一个按钮清空整个会话的阻塞条件。

卡片草稿在进度刷新时保留；提交携带幂等键和服务端状态版本，重复提交只执行一次。版本或依赖变化后拒绝旧表单并要求查看更新后的卡片。用户选择保存为真实用户消息及不可变操作事件，回执只报告程序已完成的动作。结构化接口见 [Harness 存储与接口契约](harness-data/storage-and-api.md#55-结构化待处理卡片)。

### 9.3 最终 JSON

达到 7.4 的交付条件后，Harness 保存最终 `nexo_graph` 版本，并在对话中提供结果摘要、JSON 查看、复制和 `.json` 文件下载，无须额外确认。

- 文件根对象为第 6 节定义的 `Project`，完整包含已确认章节及互动内容，并通过当前绑定的 `nexo_graph` Schema 和 8.2 的程序检查。
- 展示、复制和下载均读取同一已保存产物版本；下载动作不重新调用模型生成内容。文件为合法 UTF-8 JSON，不包含 Markdown 代码围栏、说明文字或 Harness 信封。
- 阶段草稿可在对话内查看，并明确标记草稿状态；只有满足交付条件的版本展示为最终结果。交付后的修改另存版本，历史结果仍可读取。
- 产物版本、确认依据和审核记录保存在 Harness 中，不额外加入 Graph 字段。

首版界面与平台接入的交付范围为上述对话页面、同页配置与数据可视化区、平台账号下的历史恢复及 Graph JSON 导出。Nexo 剧情树／剧本编辑器嵌入、Nexo 工程自动写入与发布不纳入首版。

### 9.4 验收

用户能够在一个对话页面内完成一次改编；必需的创作决策、阶段确认和暂停处理均有直接可操作的按钮或输入框，不依赖用户猜测应发送哪句话；所有配置可从同页入口调整，并遵守配置版本生效规则。同一账号重新登录后能够继续原会话并查看后台进度，最终下载的 JSON 与服务端交付版本一致，满足既定 Graph 契约。

## 10. Harness 内部数据与可视化

### 10.1 数据结构与存储

内部记录使用 [Harness 数据契约](harness-data/README.md) 与 [records.schema.json](harness-data/records.schema.json)，版本 `1.0.0`。它们服务于运行、持久化、恢复和页面展示；业务内容继续绑定第 6 节 output_type，最终 Graph 不添加这些内部字段。

| 数据组 | 记录类型 |
| --- | --- |
| 项目与历史 | Project、Conversation、HistoryRecord |
| 工作上下文 | WorkSession、SessionItem；工作摘要保存为内部纯文本 `work_summary` 产物版本 |
| 产物与依据 | Artifact、ArtifactVersion、ArtifactState、Decision、Confirmation、Dependency |
| 运行调度 | Task、Run、QueuedRequest、Checkpoint |
| 调用与配置 | ConfigVersion、ContextSnapshot、ModelCall、ToolCall |
| 内容与操作 | Blob、RuntimeEvent、IdempotencyRecord |

共 22 种记录。公共字段包含记录类型、契约版本、UUID、项目归属和创建时间；可变状态增加更新时间与并发版本。产物与决策使用稳定逻辑 ID 和递增内容版本，引用与现有 EvidenceRef 兼容。历史消息、产物内容版本、确认和调用快照保留原记录；当前状态单独维护，修改不覆盖旧依据。

PostgreSQL 表保存完整记录及用于外键、索引和并发检查的投影字段；大原作、附件与大 JSON 使用带内容哈希的 Blob。文件就绪后内容不可替换，修改另建 Blob。数据库结构、固定版本解析、事务与准确接口参数见 [storage-and-api.md](harness-data/storage-and-api.md)。

内部数据 Schema 由开发维护，页面提供可视化及只读 JSON；第 3 节允许编辑的模型 output_type 与内部存储 Schema 分开管理。

### 10.2 同页可视化

在对话页面增加默认收起的“运行与数据”区域，全部记录均提供查看入口，具体交互与验收见 [inspector.md](harness-data/inspector.md)。

| 视图 | 展示内容 |
| --- | --- |
| 记录详情 | 中文字段、类型、状态、固定版本、原始内容或内容引用；可切换只读 JSON |
| 历史与来源 | 从决策／确认追溯原始用户消息，再跳到被确认的版本和具体范围 |
| 任务时间线 | 任务、各次运行、工具调用、Steer／Queue、暂停、检查点与恢复 |
| 产物与版本 | 当前有效版本、草稿、正文／字段差异、确认范围与依赖有效性 |
| 依赖关系 | 当前记录的直接上游和下游，关系图与等价关系表；关联可继续展开 |
| 实际上下文 | 本次调用真正使用的 instructions、历史、摘要、材料、工具定义，以及省略原因和固定配置 |
| 用量与配置 | 调用耗时、token、已知／估算费用、预算与追加记录；运行配置和当前发布配置的差异 |

所有记录按项目权限读取，支持筛选与游标分页；默认每页 50 条、最多 100 条，依赖图默认一层、最多 50 个节点。页面读取不调用 Agent、不改变状态；敏感凭据及模型隐藏思维链不进入展示。记录修订通过既有对话和配置操作产生新版本或事件，数据详情不提供任意改库入口。

用户可以始终在主对话完成改编，也可以随时展开内部数据查看运行依据。实际调用快照与配置区的输入预览分别标记；查看旧记录不会用当前配置重新拼装后冒充当时输入。

### 10.3 数据契约验收

[合成示例](harness-data/examples/records.example.json) 覆盖全部记录类型，用于结构验证和可视化联调。开发验收要求记录通过内部 Schema、跨项目关联被拒绝、重复写入不产生重复结果、确认准确关联原话及版本、压缩后仍能查原始历史，以及所有记录均可在同页查看。该验收不扩展首版 Graph 的两项程序检查，也不引入整个 Harness 的效果评测。
