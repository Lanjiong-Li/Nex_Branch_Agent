# 运行状态机与调度契约

| 项目 | 定义 |
| --- | --- |
| 契约版本 | `1.0.0` |
| 适用范围 | 分支 Agent 服务端任务、Runner 调用、控制消息、队列和故障恢复 |
| 业务规则 | [开发文档第 4、7 节](../分支Agent开发文档.md) |
| 数据与接口 | [Harness 数据契约](../harness-data/README.md)、[存储与接口](../harness-data/storage-and-api.md) |
| 检查点状态 | [checkpoint-state.schema.json](checkpoint-state.schema.json)，绑定 `Checkpoint.cursor.handler_version=runtime.v1` |

状态机由 Python 调度层执行。模型负责解释需求和生成内容，不能自行签发确认、改变任务状态、解除预算暂停或安排未经授权的下一阶段。本文的表是开发执行契约；未列出的转移拒绝为 `invalid_state`。

## 1. 执行单位与状态归属

| 对象 | 定义与完成含义 |
| --- | --- |
| Task | 用户授权范围内的业务任务；可以跨多个阶段、Run、暂停和恢复。阶段／章节可作为子任务。只有本任务范围的产物、确认及检查条件全部满足才成功 |
| Run | 一个受控执行段。`execution_kind=runner` 至多发起一次 `Runner.run()`；`recovery` 只核对和处理已保存结果、工具与程序写入，不发模型请求。段结束后关闭，后续执行新建 Run |
| ModelCall | 一次实际模型请求尝试；网络重试分别保存 attempt，同一逻辑模型轮次复用 operation_id |
| QueuedRequest | 一条已经接收、尚待纳入或调度的 Steer／Queue 请求；请求被派发不等于对应业务任务完成 |
| Checkpoint | 可恢复的应用状态快照；不保存活着的 coroutine，也不假设重启后 SDK 内存仍存在 |

示例：Step9 返回完整设计后，Run 可以是 `succeeded`，阶段 Task 是 `waiting_user`。用户确认后可直接将该阶段 Task 标为 `succeeded`，再调度 Step10；不必为登记确认重新调用生成 Agent。

一个会话首版只有一个自动生产调度通道。生产任务释放执行资源等待用户时，协调 Agent 可以处理确认、补充和查询。不同会话或已获准的独立子任务可并行，但同一 WorkSession 永远只有一个写入者。实际进入阶段仍检查原作／产物版本、所需确认、依赖、授权范围、配置兼容和预算；阶段顺序沿用主文档第 7 节。

### 1.1 父子任务

整剧任务是工作流根 Task，阶段／章节任务为其子任务，`workflow_root_task_id` 固定引用这个根。预算按 `budget_root_task_id` 聚合；父子汇总不能重复计费。

- 子任务等待确认且没有其他可执行工作时，父任务为 `waiting_user`。
- 必需子任务暂停／失败时，父任务为 `paused`，注明被阻塞的子任务；其他已获准且不依赖该缺项的任务可以继续。
- 根任务自身预算耗尽或被停止时，整个预算／停止范围内不得发起新调用。
- 父任务只有所有必需子任务成功且自身交付条件通过后才能 `succeeded`，不能把一章生成结束当作整剧完成。
- 同一工作单元使用持久 `work_key`，包含工作流、阶段、章节／批次和生成代次。manager 重复调用与明确指向该已有工作的排队请求复用同一工作单元；用户明确要求重新生成才创建新代次。

## 2. Task 状态转移

| 当前状态 | 事件与条件 | 新状态 | 同时执行 |
| --- | --- | --- | --- |
| queued | 调度占有成功，输入、授权、配置、依赖和预算齐备 | running | 固定输入与配置，创建 Run，保存开始事件 |
| queued | 缺少必需材料／创作选择 | waiting_user | 保存具体问题、固定对象和继续位置；释放槽位 |
| queued | 预算、配置或结果核对阻塞 | paused | 保存暂停原因，不创建模型请求 |
| queued | 目标已由已保存结果／子任务满足，且全部完成条件通过 | succeeded | 直接提交完成，不为改变状态调用模型 |
| running | 产物已保存，但本任务仍有获准且可直接执行的工作 | running | 关闭当前 Run，提交检查点后调度下一工作单元 |
| running | 缺材料、需要创作取舍或等待阶段确认 | waiting_user | 保存产物／问题及待处理项，关闭当前 Run、释放资源 |
| running | 达到轮次／费用／耗时／重试／修复上限，或操作未明 | paused | 保存实际用量、计数和可恢复位置，设置相应队列 hold |
| running | 依赖变化，需要先判断影响 | paused | 原调用结果只归档；启动获准的影响检查，不推进受影响生产 |
| running | 本任务授权范围的完成条件全部通过 | succeeded | 保存结果、完成事件和交付引用；不增加最终审核确认 |
| queued／running／waiting_user／paused | 原任务身份或必需数据已不可恢复，无法在原范围继续 | failed | 保存不可恢复原因；修正需求后新建关联任务，不伪造成功 |
| running | 用户停止请求提交 | stopping | 持久停止意图，禁止新调用，取消本地执行并处理在途操作 |
| queued／waiting_user／paused | 用户停止，仍有活动执行或未明在途操作 | stopping | 持久停止意图并撤销推进资格；无本地执行时可立即完成停止收尾，远端 unknown 独立保留 |
| queued／waiting_user／paused | 用户停止，且没有在途调用 | stopped | 保存停止事件、队列 hold 和现有进度 |
| waiting_user | 明确答复只解决部分待处理项，或收到普通查询 | waiting_user | 保存实际答复／查询结果，不假定剩余问题已解决 |
| waiting_user | 所有相关待处理项已解决，仍有获准工作 | queued | 重检依赖，关闭旧 Run，不重复生成已经接受的产物 |
| waiting_user | 确认已完成，且本任务范围至此结束 | succeeded | 登记生效和完成；父任务按范围决定下一步 |
| waiting_user | 上游变化需判断影响，或后续处理已触及运行约束 | paused | 保留待用户项，记录真实阻塞；不能以旧确认直接推进 |
| paused | 用户明确继续，暂停条件已处理；或 dependency_changed 已被合法自动影响处理解除 | queued | 核验检查点、输入和余额；保存恢复依据，旧消耗不清零 |
| paused | 影响检查确认需要新的用户取舍；或 child_blocked 已变为只等待用户答复 | waiting_user | 保存具体待用户项，解除已失效的对应 hold；其余有效 hold 保留 |
| paused | child_blocked 的必需子任务已恢复／完成，且不存在其他暂停原因 | queued | 重检剩余工作与依赖；父任务聚合状态不另造一次子任务 |
| stopping | 本地执行已退出，或停止宽限到期并已撤销写入资格 | stopped | 关闭本次执行，剩余外部操作保持 unknown／在途记录 |
| stopped | 用户明确要求恢复该任务，恢复检查通过 | queued | 创建后续 Run，旧 stopped Run 保持原状 |
| running | 服务故障后成功取得接管资格，恢复条件齐备 | queued | 旧 Run 记 interrupted；消耗一次自动恢复名额并承接轮次余额 |

`succeeded / failed` 没有恢复到 running 的转移。后续修改或重做创建新 Task 并关联旧产物。`stopped` 允许明确恢复。`paused` 不表示内容等待确认；确认使用 `waiting_user`，避免一个“暂停”覆盖所有情况。

### 2.1 暂停与等待原因

| 原因 | 解除方式 |
| --- | --- |
| `turn_limit / cost_limit / active_time_limit` | 明确继续并采用获准的新限额／轮次额度，重新检查余额 |
| `retry_exhausted / repair_exhausted` | 明确继续，记录额外允许的尝试／修复额度；原计数不清零 |
| `configuration_error` | 修正配置后明确恢复；需要新配置时显式迁移并创建新 Run |
| `operation_uncertain / usage_uncertain` | 先核对未明操作／计量；仅收到“继续”不能把未知变成成功或零费用 |
| `output_limit_exceeded` | 已收到因 `max_output_tokens` 截断的响应；保存实际终态和用量，暂停且不将部分输出作为产物。需要新输出上限时，新任务使用已发布配置；继续旧任务仍沿用冻结配置 |
| `response_incomplete / response_failed / model_refusal` | 展示供应商返回的安全原因分类，保留响应与用量；根据具体原因处理，不归为网络结果未知 |
| `dependency_changed` | 影响明确且修复在原授权内可自动解除；新创作选择转 waiting_user |
| `recovery_exhausted / checkpoint_invalid` | 明确人工恢复并具备有效恢复依据；不能靠进程重启清零 |
| `child_blocked` | 被依赖子任务恢复或有获准替代材料；无关子任务不因此停止 |

待用户项明确区分 `confirmation / question / decision`，保存问题消息 ID、目标固定版本、范围、答复来源和状态。不以“用户发来了新消息”作为全部等待条件已解除的判据。

## 3. Run 状态与关闭规则

| 当前状态 | 事件 | 新状态 | 业务 Task 的典型结果 |
| --- | --- | --- | --- |
| created | Session 租约和调用前检查通过 | running | running |
| created | 准备阶段发现可恢复阻塞 | paused | paused |
| created | 尚未发出请求即收到停止 | stopped | stopped |
| running | Runner 正常返回完整结果，或 recovery 段完成其程序处理 | succeeded | 仍执行、等待确认或完成，按任务条件判断 |
| running | 返回 needs_input 或明确的用户等待中断 | waiting_user | waiting_user |
| running | 达到调用轮次限制，或主动在安全边界因预算／依赖收尾 | paused | paused |
| running | 本次调用失败且自动重试已耗尽／输出无法解析 | failed | 按剩余额度修复，或 paused；不直接把业务 Task 视为不可恢复 |
| running | 停止请求提交 | stopping | stopping |
| stopping | 本地退出或撤销写入资格后宽限到期 | stopped | stopped |
| created／running／stopping | 执行进程失联且租约过期，由接管者核实 | interrupted | 恢复、保持停止或 paused，按第 6 节裁决 |

Run 的 `succeeded / waiting_user / paused / failed / stopped / interrupted` 均表示本次执行段已关闭：设置 `finished_at`、释放租约；Task 无活动 Run 时 `current_run_id=null`。后续执行创建新 ID，不覆盖旧 Run 的模型轮次、配置或依据。已关闭 Run 的迟到结果只能补原始调用记录和用量，不能把 Run 改回 running。

recovery Run 使用相同的 created／running／结束转移，成功处理程序动作时转 succeeded，但 `max_turns=0`、`model_turns_used=0`，不得调用 SDK。需要新模型请求时先关闭 recovery Run，再建立继承余额的 runner Run；余额为零时仍可完成纯工具／保存操作，不能建立可发模型的 Run。恢复执行旧工具时，ToolCall.run_id 为当前执行段，model_call_id 仍指向真实旧模型调用；只有同 Task 且恢复链、原请求与固定输入核验通过才允许此关联。

recovery 段使用 `agent_key=runtime_recovery` 标识程序处理器，不新增专业 Agent。所有 ModelCall 必须属于 runner Run；工具恢复不复制旧 ModelCall。

调用返回 `ready` 不自动代表业务质量通过；JSON 校验、正文审核及必要确认仍按主文档处理。调用返回前若停止／依赖变化已提交，返回内容归档并保留原输入版本，不按原计划自动生效。

## 4. 控制消息与队列

### 4.1 Steer

1. 接收时原子保存原消息、用户选择、目标 Run 和待纳入记录；按服务端事件顺序排序。
2. 下一次安全边界读取所有尚未处理的 Steer。安全边界包括模型请求前、工具执行前、结果保存后的调度点和产物生效前；不在已经发出的请求里替换输入。
3. 按实际内容区分查询、修正或停止。查询仅回答问题；变更固定到实际范围；冲突／歧义转具体待用户项。运行配置快照不被 Steer 改写。
4. 已开始的工具／模型操作保留原参数。新的修改若影响它的结果，结果可留作旧依赖草稿；不得绕过新要求直接生效。
5. 写入 `control.applied`，保存消息与采用它的 ContextSnapshot／确认／命令结果引用后，才将请求标记 applied。无需模型调用的命令，快照引用可空，但实际命令事件必须存在。
6. 若普通完成／停止后目标 Run 已关闭且请求尚未被处理，记 blocked 并给出 `target_not_running`；不静默改投 Queue。用户重新派发时复用原消息。唯一自动承接情形是服务故障：旧 Run 活跃时已合法接收的 Steer 可随同 Task 的已验证恢复链继续，保留原 target_run_id，并另记实际 adopted_run_id。向已关闭 Run 新提交的 Steer 不适用此例外。

### 4.2 Queue 的调度时机

队列按会话的接收序号处理。自动出队的时机是当前授权生产 Task 完成，或当前生产到达 waiting_user 的稳定检查点；普通模型轮次结束和工具返回不自动让 Queue 抢占尚在继续的生产任务。

| 当前生产状态 | 自动队列行为 |
| --- | --- |
| running | 保存请求；优先完成当前生产或达到用户决策点 |
| waiting_user | 允许协调处理确认、补充和查询；需要未满足上游的生产请求记 blocked，不占运行槽位 |
| succeeded | 无其他 hold 时处理最早可执行请求 |
| paused（预算、错误或核对原因） | 保留请求并设置会话队列 hold；停止自动出队 |
| stopping／stopped／failed | 保留请求并设置 hold；不自动启动下一项生产 |
| 无生产任务且 gate 开放 | 处理最早可执行请求 |

阻塞范围限于该会话的自动队列和实际受影响任务。无关 Session 中已运行的独立任务继续。用户明确提交的新查询、状态读取和控制命令仍可处理；它们不解除原生产任务的暂停，也不能通过新建同一生产任务绕过预算。

### 4.3 避免等待死锁与重复生产

- 缺依赖的请求写 `blocked_reason` 并释放槽位。调度器继续按序检查后续条目，允许处理不推进冲突生产的查询，或能解除已有等待点的确认／补充／控制；不越过前面的变更请求执行与其冲突的生产。
- 例如队列先是“生成第 1 章 Step10”，后是“确认第 1 章 Step9”：前者 blocked，后者固定确认 Step9 后，重新检查前者。
- 同一会话首版最多同时运行一个队列意图解析任务；解析时请求仍为 pending，仅在会话控制投影中登记占有者和解析任务 ID。解析完成后再将有实际承接 Task 的请求记 dispatched；依赖不足或意图含糊则记 blocked。查询／确认可由该协调任务直接完成，回执仍记录真实 Task。blocked 项仅在相关依赖、答复、gate 或明确重新派发事件发生后重检，不忙轮询或重复询问。
- 确认绑定消息提交时明确指向或实际展示的版本。引用歧义时询问；出队时出现新版不得把“就这样”自动改绑新版。若被确认版本的依赖已变化，可保留针对旧版的确认，但不直接放行失效生产。
- Queue 内的确认仅在轮到处理时生效，接收时不修改当前运行输入。确认完成后唤醒 manager；重复调用与指向同一 `work_key` 的排队请求共享一个生产子任务，并各自记录关联回执。
- manager 一轮已推进任务但尚未到等待用户或完成状态时，Harness 创建内部续跑消息和独立队列项；它沿用原授权范围，不视为新的用户确认。若内部续跑没有推进任务，则以 `manager_no_progress` 暂停，避免空转循环。
- 明确要求“重新生成”“另给一版”或改变创作约束不是重复请求，创建新生成代次并保存新版本；不能用相似文本去重。

### 4.4 QueuedRequest 状态

| 当前状态 | 事件 | 新状态 |
| --- | --- | --- |
| pending | Steer 实际纳入／命令实际处理 | applied |
| pending | Queue 意图已明确，实际派发业务 Task／完成协调处理，或关联已存在的同一工作单元 | dispatched |
| pending | 目标关闭、依赖缺失或 gate 阻塞 | blocked |
| blocked | 对应条件已解决且用户原意仍明确 | pending |
| pending／blocked | 用户明确取消请求或明确用另一条请求替代 | cancelled |

applied、dispatched、cancelled 为该请求的终结状态；执行进度通过所关联 Task 查询。请求已接收、已派发、业务已完成分别展示。Steer 不得转成 Queue，除非用户明确重新选择并产生新的派发操作记录。

### 4.5 Queue gate

当前测试版关闭费用门禁：调度读取时忽略旧 `usage_uncertain` hold，以及依据事件明确为 `cost_limit` 的 `budget_limit` hold，原始记录不删除。耗时、轮次和其他错误 hold 仍有效。旧费用暂停可通过界面直接继续，无需追加或核实费用；修改策略本身不自动重启旧暂停任务。真正远端结果未知仍按 `operation_uncertain` 阻止重复调用。

gate 保存 `conversation_id`、并发版本以及 hold 条目：原因、阻塞 Task、依据事件。进入停止、超限、恢复失败或不可恢复失败时与状态事件同事务设置。任一有效 hold 尚未解除，都不自动出队。

解除有两条路径：相应任务经过合法恢复且阻塞已处理；或用户明确“继续处理排队消息”，调用 `resume_queue`。后者只解除队列调度 hold，不恢复被停止／超限的 Task、不清零预算、不跳过请求依赖；依赖旧暂停任务的请求仍 blocked。普通新消息、配置发布、页面重连及服务重启不清除 gate。

### 4.6 直接操作待处理事项

`pending_user_items`、暂停任务和受阻队列在主对话中生成结构化卡片。每张卡片有稳定 ID、服务端状态指纹、真实原因、固定引用及可执行动作。确认、逐题回答、修改要求和恢复选择由按钮／表单直接提交；不额外调用协调 Agent 识别按钮含义。控制输入按真实用户消息保存，并生成不可变 `action.applied` 操作事件，引用用户选择、绑定目标及执行回执。

提交时重检任务、固定材料、依赖、配置及队列阻塞依据。陈旧卡片返回 `action_stale`，不能把旧回答自动应用到新版本。重复请求按幂等键返回原回执；多个问题分别处理，只有当前任务需要的全部回答齐备后才继续。已知失败后的新配置重做保留旧 Run 与计费事实，显式替代的任务不再被自动恢复。重新开始必须实际重做授权阶段，不能因发现旧有效产物而跳过。

队列按请求处理。解除或替代一个任务的阻塞不表示其他排队请求获得执行授权。已知终态但费用未知的调用可依据用户填报记录费用，也可在用户明确接受未知旧费用后创建独立预算的新任务；不可把未知费用记为零。仍存在远端结果未明的操作时，相关重做动作禁用并说明原因。接口与字段见[结构化待处理卡片](../harness-data/storage-and-api.md#55-结构化待处理卡片)。

## 5. 并发事件与执行优先级

所有控制意图、完成提交和生效操作在会话／任务锁内串行裁决，以服务端提交事件序号为准；客户端时间和网络返回时间不作为覆盖依据。原始响应及计量可以先归档，业务状态与产物生效必须在锁内重新检查。

每次调度和生效前依次检查：写入资格与权限 → 当前 Task 及其约束祖先的已提交停止意图 → 本任务暂停原因与预算 → 待处理 Steer → 依赖与确认 → 当前结果提交／下一次调用。自动出队还必须检查该会话 queue gate；gate 本身不阻断其他已授权的无关任务或用户明确的新查询。这个顺序用于处理已提交事实，不撤销之前已经合法提交的结果。

| 竞争情况 | 裁决 |
| --- | --- |
| 停止先提交，随后模型返回 | 保留响应和费用；不继续工具或下游生成，不自动生效 |
| 完成先提交，随后停止 | 返回已经完成的实际状态；不回滚产物、不伪造停止成功 |
| Steer 先提交，随后原答案返回 | 完成前处理该 Steer 的实际意图；查询可回答，变更则按依赖范围处理原答案 |
| Run 已关闭，随后 Steer 接收 | 保存消息并返回目标关闭；不投向其他任务 |
| 达到预算限制与结果返回同时发生 | 已发生的结果和费用必须保存；完成尚未提交而限制已触发时进入 paused，结果留作草稿／待交付版本，明确继续后可复用，不重新生成；已经先提交的完成状态不追溯回滚 |
| 确认与上游修改并发 | 事务内重检固定版本、状态版本和依赖；失败返回竞争／需复核，不扩大确认范围 |
| 租约过期后旧 worker 返回 | 拒绝旧 fencing token 推进状态；可信回收流程仅归档原操作结果和用量 |

停止默认作用于页面所指的业务根 Task 及其子任务；明确指定章节／子任务时限于该子树。`interrupt_task` 为业务停止入口，`interrupt_run` 复用相同规则停止该 Run 所属 Task；父任务不会因子任务停下而另建同一工作绕过停止。等待用户、没有活动 Run 时也可以停止 Task。

收到停止后先落库再取消本地执行。默认宽限 30 秒；到期撤销原执行者写入资格，任务显示 stopped，尚未核实的外部请求仍单独显示在途／unknown，继续归集可获得的费用。stopped 表示 Harness 不再推进该任务，不声称供应商请求已经取消或不再计费。

## 6. 检查点与服务恢复

### 6.1 保存边界

在开始模型请求前、模型响应归档后、工具结果保存后、产物与确认生效后，以及等待／暂停／停止和阶段切换时保存检查点。对应业务写入、计数、Task／Run 状态、事件与新检查点引用必须同事务提交。

沿用现有 Cursor.kind，不依赖新增枚举；`cursor.state.next_action` 明确下一动作。模型响应已保存但工具尚未执行时，next_action 为 `execute_tools`；不能因 Cursor.kind 相同就再发一次模型请求。

检查点至少保存：工作流根与 work_key、下一动作、运行链与轮次余额、自动恢复累计次数、未纳入控制请求、固定版本待用户项、队列 gate 快照、停止意图、未明操作及核对依据。外层 Checkpoint 继续保存 Session 代次、配置、输入引用、已完成操作和用量。

通过恢复载荷 Schema 后还须验证：所有引用属于同项目和对应任务／会话；轮次 `used <= limit`，未完成预留 operation_id 不重复且数量不超过 used；恢复计数与额度账本相符；待确认目标、消息和条目确实存在。恢复时重新读取当前控制账本并处理检查点之后收到的消息，不能只读取快照中的 pending 列表。快照不是覆盖当前事实的写入指令。

### 6.2 自动接管流程

1. 按数据库时间检查 Run 和 WorkSession 的租约；未过期不接管。默认租约 60 秒、心跳 15 秒；续约不改变 fencing token，接管递增令牌。
2. 先读取当前 Task、停止意图、queue gate、最新有效检查点与操作账本；旧检查点不能把较新的暂停、确认、用量或控制记录覆盖掉。
3. succeeded／failed 不重跑；waiting_user 保持等待；stopped 保持停止；stopping 完成停止收尾；已因预算、重试、修复或恢复上限暂停的任务保持暂停。
4. 对因服务故障中断、仍获准执行的任务，在同一事务占有接管权、递增自动恢复计数并标记旧 Run 为 interrupted。自动恢复默认最多 3 次／Task，按 5、30、120 秒退避；跨进程重启累计，不在成功一轮模型调用后清零。
5. 建立不发模型的 recovery Run 核对已完成和未明操作，验证输入、配置、Session 协议和预算，处理可安全完成的工具／程序动作。仍需模型且余额足够时，关闭恢复段并建立 runner Run，沿用原快照及剩余轮次；否则保存具体暂停／等待或完成状态。
6. 在已保存结果之后继续：有模型结果先处理工具／产物，有已保存产物先判断确认或交付。页面没收到通知时只补发事件／结果，不重新生成。

发现原 worker 仍持有有效租约时的查询不消耗恢复次数。一次接管及其 recovery→runner 衔接合计一次恢复尝试，在取得接管权后才计数；接管后再次崩溃也消耗该次。达到上限后，明确人工继续可启动一次人工恢复检查，但不重置自动恢复累计次数。

### 6.3 外部操作结果未明

| 操作事实 | 处理 |
| --- | --- |
| 已有持久化结果 | 复用该结果，补齐幂等业务提交，不再发相同请求 |
| 账本为 pending，且能证明尚未交给网络／执行器 | 使用原 operation_id 发起尚未执行的尝试 |
| 请求已发出或可能已发出，本地无结果 | 标 unknown；先查记录及供应商支持的响应／状态查询，不直接当作失败 |
| 已核实失败且允许重试 | 保留原失败尝试，按同一操作的剩余重试额度创建新 attempt |
| 收到 `response.incomplete / response.failed`，或明确拒答 | SDK 校验前持久化终态、响应及实际用量，ModelCall 记 failed；截断、拒答及失败响应不能作为有效产物或恢复结果 |
| 已收到终态，但供应商未返回用量／费用无法计算 | 结果分类保持已知；费用额度启用时，新调用仍由 `usage_uncertain` 阻断，不能把 failed 当作零费用 |
| 首版只读工具结果未明，可固定原读取版本且无副作用 | 允许登记新 attempt 后重新读取，消耗原重试额度；不将新结果冒称原尝试已成功 |
| 无法核实模型请求或有副作用的外部操作 | paused：operation_uncertain；不自动重发。明确继续仍须先核验结果、重复风险和预算 |

服务端不承诺模型请求“恰好一次”；它保证已提交业务写入不重复、未明调用被记录、计量不以未知当零。费用／耗时无法确定且相应限额启用时暂停新的受限调用。

页面以对应 Task 的最新 Run 显示中文原因、错误码及受控诊断字段；父任务 `child_blocked` 展示当前阻断子任务的实际原因。原供应商消息、密钥和响应正文不直接拼入错误提示。旧版误分类只能凭关联调用与 SDK 的精确终态诊断显式更正，保存原记录快照及更正事件，不补造响应、用量，不自动重跑。

### 6.4 轮次、重试与恢复额度

正常新的 Runner 调用按当前固定配置获得最多 10 个模型轮次。因服务故障续接同一次未完成工作时，共用原 `turn_allowance`，不能自动获得新的 10 轮：原额度 10、已用 7，恢复 Run 最多再用 3。

每个逻辑模型轮次在发送前原子登记 operation_id 并预留一轮；网络重试复用该轮，但每次实际请求单独计费。只有能证明完全未发送的预留可以撤销，未知请求仍占额度。重启时按预留账本与调用记录核对，不能仅依赖 SDK 内存计数。

`Run.model_turns_used` 为本次调用内的轮次，恢复链总用量保存在额度账本和检查点。完成必要工具／保存后若不需新模型调用，可以在剩余轮次为零时结束；若仍需模型则暂停。用户明确继续触顶任务时可获新的轮次额度，保存授权来源并保留旧额度和全部历史计数。

临时失败仍默认最多重试 2 次，输出修复仍默认最多 2 轮；内部 SDK 重试必须关闭或纳入同一 operation 账本，不能叠加上限。首次以外的尝试数从 ModelCall／ToolCall 记录计算，修复数在开始修复前落库；达到上限后的人工继续要记录追加量，不将计数归零。正常完成后的下一阶段可使用新的 Run 额度，故障恢复不得冒充下一阶段。

## 7. 持久调度与幂等规则

沿用现有事务、条件版本和幂等接口，并增加以下内部投影；它们从已提交事件／记录维护，不作为新的模型输出或可任意编辑的数据：

| 内部投影 | 主键／关键约束与用途 |
| --- | --- |
| `conversation_controls` | `(project_id,conversation_id)`；含 row_version、hold 条目、最后已采用事件序号、正在解析的队列项及协调任务引用；当前 gate 和串行队列占有的权威投影 |
| `task_runtime_controls` | `(project_id,task_id)`；恢复次数、有效追加重试／修复额度、停止意图和当前额度 ID；同事务更新并保留事件 |
| `turn_allowances` | allowance_id；归属 Task、链起始 Run、limit、used、来源事件及 row_version |
| `turn_reservations` | `(allowance_id,operation_id)` 唯一；记录轮次预留／发送／完成／证实未发送释放及关联调用 |
| `work_dispatches` | `(project_id,workflow_root_task_id,work_key)` 唯一，指向一个 Task；同一工作不能被 manager 工具调用和排队请求各派发一次 |

更新锁顺序统一为：项目级共享产物（需要时）→ 会话控制 → 按 ID 排序的 Task／逻辑产物 → Run → WorkSession → 操作／队列行。不得持有数据库事务等待网络返回。结果写入复核当前令牌与条件版本，执行一次“检查成功”不代表后续写入可省略检查。

已提交幂等结果直接重放；相同键不同请求拒绝；状态不明先核对。用户消息接收与队列登记原子提交，派发与 Task 关联原子提交，产物版本与完成事件原子提交。通知使用已提交 RuntimeEvent；SSE 重连和浏览器刷新不会创建新任务。

事件名使用 `task.transitioned / run.transitioned / control.applied / queue.gate_changed / queue.dispatched / recovery.claimed / recovery.paused / turn.reserved / operation.reconciled / checkpoint.saved`。状态事件 payload 包含对象 ID、from_state、to_state、reason、来源消息／事件和 checkpoint_id（尚未建立时可空）；每个事件记录实际事实，不用 UI 猜测或模型措辞代替。

## 8. 配置与同页展示

| 配置键 | 初始值 | 约束 |
| --- | --- | --- |
| `recovery.max_attempts` | 3 | 非负整数；0 表示不自动接管，历史计数不清零 |
| `recovery.backoff_seconds` | `[5,30,120]` | 非空的非负数数组；超过数组长度采用最后一个值 |
| `runtime.lease_seconds` | 60 | 正整数，必须大于 heartbeat_seconds 的两倍 |
| `runtime.heartbeat_seconds` | 15 | 正整数；只用于后台持有权，不向用户刷状态消息 |
| `runtime.stop_grace_seconds` | 30 | 非负整数；到期撤销本地写入资格，不声称远端已取消 |

这些参数纳入同页配置区和运行快照。新配置只影响后续正常启动的工作；故障恢复沿用原有效参数，显式迁移另记依据。队列安全规则、幂等保护、固定版本确认和租约校验不可关闭。

运行与数据区分别展示 Task 状态、Run 状态、队列 hold、待用户项、已申请停止／实际停止、恢复累计次数和下一重试时间、原轮次额度与续跑余额、未明操作及核对结果。提供继续 Task、继续队列和停止的明确入口；操作后展示实际回执，不仅切换前端标签。用户也可在对话中明确表达同样意图。

## 9. 执行验收场景

| 场景 | 预期 |
| --- | --- |
| Step9 正常返回但用户未确认 | Run succeeded、Task waiting_user；不生成 Step10 |
| 用户明确确认已展示版本 | 只登记实际范围，阶段完成并在授权范围内推进，无重复确认 |
| Queue 中生成请求在确认前面 | 生成 blocked，后续确认可解除等待；Step10 只派发一次 |
| Run 完成与 Steer 竞争 | 按提交顺序处理，消息不丢失、不自动投错任务 |
| 用户停止时模型仍在请求中 | 不再派发新调用，保留在途操作及后续可得用量；队列不自动开下一项 |
| 触顶后重启／发布配置／普通聊天 | 原任务仍暂停，计数和 queue hold 保留 |
| 10 轮用掉 7 轮后服务故障 | 自动续跑最多剩余 3 轮；恢复次数累计 |
| 产物保存后、通知前进程退出 | 恢复时只补事件／结果，不重复生成或保存新版本 |
| 请求可能已发出但结果未知 | 核对或暂停，不盲目重发、不显示零费用 |
| 老 worker 在接管后返回 | 旧令牌不能推进新任务；原结果仅按原操作归档 |
| 故障连续达到 3 次自动恢复 | paused：recovery_exhausted；等待明确人工处理 |
| 旧检查点含已解除 hold | 调度仍读当前 gate，不能借旧快照重放过时状态 |

这些是运行正确性验收，不引入 Harness 创作效果评测或额外 Graph 质量算法。
