# 上下文压缩策略开发方案

> 状态：需求对齐稿，拟议改动尚未实现。当前实现以 2026-09-26 的代码为准。本文把「压缩旧会话历史」与「处理本次超大输入／输出」分开；后者不能靠摘要替代完整业务内容。

## 目标与边界

对话协调 Agent 是主 Agent，负责对话和阶段调度。它调用 `run_stage` 工具后，Harness 创建子 Task／Run 执行相应专长 Agent；这是 manager 模式的工具调用，但当前代码并未直接使用 SDK 的 `Agent.as_tool()`。阶段工具回执只返回状态、Task ID 和固定产物引用，不把完整中间产物作为工具结果带回主 Agent。

要覆盖两类增长：

1. **主 Agent 的 Session 历史增长。** 阶段回执较短，通常不是主要开销；但主 Agent 按需调用 `read_record` 阅读候选产物、用户在聊天中粘贴长原文，或同一次运行持续多轮工具调用，都可能使主 Session 变大。
2. **子 Agent 的任务增长。** 子 Agent 的旧 Session 历史可以压缩；本次必须读取的原作或中间产物过大，需要按固定版本和完整工作范围分批；本次应生成的产物超过输出上限，需要分段生成并校验合并。后两项不是历史压缩。

任何摘要都只能是可追溯的工作记忆，不能替代必需原文、完整产物、用户确认或正式记录。原始历史、工具调用与结果、固定产物版本必须保留。

## 当前实现

| 环节 | 已有行为 | 当前边界 |
| --- | --- | --- |
| 主 Agent 的输入 | `run_stage` 返回状态和产物引用。默认协调阶段材料提供项目状态、引用目录和适用约束；业务产物正文不自动进入模型输入。 | Step2–10 候选确认前的指令要求主 Agent 调用 `read_record`。读取结果进入主 Session；聊天消息中的长原文也会进入当前请求。 |
| Session 历史压缩 | `ModelService.run` 在启动一次 `Runner.run` 前，针对当前 Session 调用 `aux.summary`。默认完整输入超过有效预算的 75%，或旧历史超过 6,000 token 时触发；目标约 50%，尽量保留最近 6 个请求组，摘要目标 1,500 token。摘要保存为 `work_summary`，旧记录和旧 Session generation 保留。 | 同一次 `Runner.run` 内，模型多轮调用及工具结果不断增加时，只校验下一次输入是否合预算，不会在两轮间再次压缩；超限可能直接报错。主、子 Agent 目前沿用同一套默认历史阈值。 |
| 子 Agent 的 Session | 各阶段有自己的或按配置共享的 Session；默认 Step2–4 各自独立，Step6 复用 Step5 的 Session。Step1 的两条视图及各窗口有独立 Session。 | 新 Session 的当前材料过大时，没有可压缩的旧历史。 |
| 当前输入材料 | 有效输入预算为 `min(配置输入上限, 模型窗口－输出预留－安全余量)`。Step1 使用全文／滑动窗口；Step2–8 在必需输入超预算时有分批子任务兜底。 | 可选材料可以裁减，必需材料不能悄悄截断。Step9–11 没有同类自动分批兜底；Step2–8 的最终聚合仍可能过大。 |
| 当前输出 | 单次输出受模型的 `max_output_tokens` 和阶段 Schema 限制；超限响应不作为有效产物。 | 目前没有通用的「分段产出、持久化、合并、最终校验」流程；历史压缩不能提高单次输出上限。 |

## 拟调整方案

### 1. 主 Agent：保持引用为主，压缩主 Session

- 保留 `run_stage` 的轻量回执。主 Agent 默认读取状态、固定引用和必要的短目录；产品界面直接从数据库展示完整候选产物，不必把展示用全文复制进主 Session。
- 调整候选确认的读取规则：主 Agent 为判断内容或回答修改意见时，按固定版本、字段或分页读取必要部分；不能把只看目录说成已审阅全文。是否需要完整阅读，由该次业务判断决定，不能仅为弹出确认卡而无条件读取所有正文。
- 对直接粘贴到聊天的长原作，先原样持久化为 `source_text`；进入协调模型请求的是来源引用和必要信息，完整原文仍可由 Step1 按既定全文／滑窗规则读取。此项需保证用户原消息与保存版本可审计关联。
- 主 Session 也执行历史压缩，但把检查点从「新 Runner 启动前」扩展到同一 Runner 的**每次模型请求前的安全边界**。只有完整工具调用／结果链可进入摘要；正在等待的工具结果、当前用户请求和待处理确认保持准确。无法安全替换 SDK 当前输入时，应结束当前 Runner 段并从持久 Session 恢复，而非在工具调用中间改写历史。

### 2. 子 Agent：区分旧历史与当前材料

- 对共享 Session 或长时间运行的子 Agent，沿用同一套可追溯历史压缩，并在安全的模型轮次边界检查。不同 Session 各自压缩，不把其他阶段的完整历史复制进来。
- 在组装本次请求前计算 instructions、工具定义、Schema、输出预留和安全余量，再给必需材料分配输入预算。保持固定 `artifact_id/version`、稳定条目 ID、原文 UTF-16 锚点、批次归属与覆盖记录。
- 复用 Step1 现有双视图滑窗、Step2–8 现有输入分批；补齐 Step9–11 的超大必需材料处理，并检查 Step2–8 最终聚合是否仍可能超过预算。分批结果只能是局部草稿；所有规定范围完成并通过跨批一致性校验，才能形成完整候选。
- 若完整产物预计超过单次输出上限，应按该阶段的合法业务单元分段产出、逐段保存并校验，最后合并和运行完整 Schema、引用、因果与覆盖检查。Step9／Step10 若要在单章内拆分，须先定义片段产物合同和合并规则；在此之前保持明确的预算阻塞，不能截断 JSON、遗漏正文或擅自改变章节边界。

### 3. 配置和审计

- 让主 Agent 与子 Agent 的历史上限、触发比例和保留轮数能够分别覆盖配置；仍以模型实际输入预算为硬约束。当前统一的 6,000 token 历史上限应依据运行数据评估，不能因为模型窗口大就盲目调高。
- 记录每轮的固定输入、Session 历史、材料、工具结果、输出预留、压缩前后 token、批次覆盖和输出分段状态，便于区分「旧历史太长」「本次材料太大」「输出太大」。
- 摘要 Agent 是否从默认复用对话协调 Agent，改为可在配置页单独选择模型和编辑 instructions，作为实现前需确认的配置项；`aux.summary` 仍只是内部阶段标识。

## 实施顺序与验收

1. 先用已有 Agent Run／ContextSnapshot 统计主要 token 来源，并调整主 Agent 的候选读取路径；保持工具回执只返回引用。
2. 将压缩检查延伸到同一 Runner 内的安全模型轮次边界，验证工具调用成对、当前请求保留、失败时原历史不变。
3. 为未覆盖的阶段补输入预算规划与完整覆盖校验；对聚合结果再次做真实请求预算检查。
4. 按阶段定义大输出片段合同、持久化与合并校验，再启用自动分段；未定义的阶段继续明确报预算问题。
5. 最后提供必要配置入口和运行数据可视化，并用长原文、长候选、多轮工具调用、单章超大 Graph、输出截断、版本变化及中途恢复验证。

验收标准：主 Agent 不因阶段工具回执被动收到完整产物；每次压缩后仍可定位原始历史；每个必需材料范围和最终产物都完整可核验；任何超预算或失败都保留已提交进度，不把摘要、索引或片段冒充完成结果。
